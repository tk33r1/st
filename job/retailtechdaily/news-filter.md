# ニュース採否のJev判定

実装済み（2026-10-04）。正本はコード。

国内・海外のRSSニュース候補の内容を、Jevの採否基準付きyes/no質問1問で判定する。
質問と基準の正本は `.github/scripts/daily_news_filter.py` の `POLICIES['retail']`。
比較テストも同じ基準と応答解析を使う。採用境界は0.5。

処理順は、RSS取得 → 既掲載とURL重複の除外 → 日付の確認 → Jevの内容判定 →
候補内の見出し重複の除外 → 並べ替え → 従来のAIによる記事選定・要約。
日付・URL重複・見出しの重複・件数上限は従来の処理を使う。
NG記事や古い記事の見出しが、冒頭の似た掲載対象の記事を先に消さないよう、
候補内の見出し重複は内容判定のあとに除く。
Jevに渡すのは見出し・RSSの説明・配信元だけ。記事全文やリンク先の補完はしない。

従来のニュース除外語は正常なJev判定に適用しない。
一般検索の `-レシピ`・`-セール`・`-スイーツ` も外し、食品売り場やキャンペーンに伴う
技術導入を内容の判定前に落とさないようにした。
公式の技術導入発表や、セルフレジの使い勝手への生活者の反響も対象。
食品の商品紹介だけ、一般AI記事、投資情報、同名別物などは対象外。

並列数は4、リクエストのタイムアウトは8秒。
API障害・不正な応答は当該記事だけ従来ルールで判定し、残りのJev判定を続ける。
キーがない・モデル設定を読めない場合は、その候補群に従来ルールを使う。
障害時に採否の精度が同じとは限らないため、従来ルールを使ったことを警告・集計に出す。
記事本文・キー・上流の応答本文は警告ログに出さない。

GitHub Actionsでは、既存の共通生成workflowが `TYPESAFE_API_KEY` を渡す。
手元では同名の環境変数、`MAGI_TYPESAFE_API_KEY`、`workers/magi2/.dev.vars` の順に読む。
モデルIDは `config/ai-models.json` を `ai_model_registry.py` 経由で読む。
週次のモデルスモークテストは、食品売り場の技術導入・英語の店舗技術記事・食品紹介だけ・
一般AI記事を本番と同じ質問と形式で確認する。

外部通信なしの検証は `.github/scripts/test-daily-news.py`。
ニトリのニュースにはこの判定を適用していない。
比較結果は [ニュース採否のJev比較テスト](../nitoridaily/news-jev-evaluation.md) を参照。
