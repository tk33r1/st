# MAGIの公開前検査

実装済み（2026-10-25）。正本はコード。Webの動作確認とAndroidの模擬プラグインだけを根拠に配布しない。

## 公開を止める場所

| 対象 | 必須検査と停止位置 |
| --- | --- |
| Pages | `build.sh`の最初に会話イベントの一致を検査。Cloudflare上では、同じコミットの`magi-chat-validation.yml`が成功するまで最大15分待つ。未実施・失敗・取消・通信失敗・時間切れは非ゼロ終了し、公開を止める |
| magi2 Worker | `deploy-worker-core.yml`が同じSHAの上記workflowを先に実行。成功後にだけ秘密の同期・デプロイへ進む |
| Android Release | `magi-release-gate.mjs --publish`だけを通常の配布入口とし、全結果と最終APKを照合してからdraft作成・アップロード・実ダウンロードのhash照合・公開の順に進む |

GitHubのCIが緑というだけでAndroidの公開を許可しない。最終署名APKの本番疎通は別の必須条件である。GitHub/Cloudflareの管理者による直接操作を技術的に禁止するものではないため、管理画面や低水準CLIでゲートを迂回しない。

Pagesは公開リポジトリのActions APIを読み取る。GitHubの読み取り制限が問題になる環境では、Pages側へActions Readだけの`MAGI_CHECK_GITHUB_TOKEN`をsecretとして設定できる。取得失敗を合格扱いにはしない。GitHub Actionsの`[skip ci]`はPagesもビルドしないため、公開したい修正には付けない。

## 自動の合成検査

- Worker・トップ・PWA・Javaのイベント一覧が一致すること。今回の`session`欠落を再導入する否定テストも行う。
- Web/PWAは各10条件、Androidは11条件。通常／一時×パーソナライズ有効／無効の初回・継続と、通常会話の保存復元を検査する。Androidにはバックグラウンドでの受信完了・プロセス終了後の一度だけの復元も含む。
- 質問ごとに固有の合成文と回答を使い、新しい回答の増加・表示・正常終了・要求1回を確認する。継続では前の回答が送信文脈へ含まれることを確かめる。
- Androidは`st.tk.magi.b3probe`の本物のプラグイン・OkHttp・Javaのイベント選別・耐久保存を通す。画面を模擬プラグインへ差し替えない。検査対象APKのインストール実体のhashと同梱wwwも照合する。
- 一時チャットは設計どおりWebView側の経路を通す。HTTPとWebSocketの両方を合成応答へ閉じ、通常のネイティブ受信は固定ループバックへ送る。本番アプリのデータは消さず、別ID検証アプリだけを初期化する。
- CIはLinux/Androidエミュレーターで実施する。ローカルでは同じ検査を接続済みの実機で実行できる。検査結果はGit対象外の`workers/.wrangler/magi-chat-gate/`へ出す。

ローカル例（接続先とADBの場所は手元のものを使う）:

```sh
node --test .github/scripts/test-magi-chat-contract.mjs .github/scripts/test-magi-release-gate.mjs .github/scripts/test-magi-chat-publication.mjs
node .github/scripts/test-magi-chat-matrix.mjs
# npm ciとcap sync後、magi-app/androidからビルドする。Windowsはgradlew.bat。
./gradlew assembleDebug testDebugUnitTest -PmagiB3Probe=true --no-daemon
adb -s <device> install -r app/build/outputs/apk/debug/app-debug.apk
# 次のコマンドはリポジトリ直下から実行する。
node .github/scripts/test-magi-chat-matrix.mjs --android --adb=adb --device=<device> --apk=magi-app/android/app/build/outputs/apk/debug/app-debug.apk
```

`test-magi-chat-matrix.mjs`の`--android`なしはWeb/PWAの合成検査であり、Android実処理を確認したことにはしない。

## 最終APKと本番確認

1. 最終コミットを確定し、通常の署名APKを作る。`verify-apk.py --commit`で全www・版・署名を検査する。試作用の`--working-tree`は配布不可。
2. 最終APKを実機へデータ保持で上書きする。署名鍵は元の場所で使用し、検査のために複製しない。
3. 本人の許可と既存予算の範囲で、次の観測器を起動する。観測器は入力・設定変更・送信を自動実行しない。画面のパーソナライズ有効を確認した後、利用者にその実行だけの合成文を表示する。

```sh
python magi-app/scripts/record-production-smoke.py --adb <adb> --device <device> --apk <signed.apk> --report workers/.wrangler/magi-chat-gate/production.json
```

4. 利用者が新しい通常チャットから合成文を送る。観測器は送信開始、新しい固有回答、正常終了を確認する。最終APKと端末APKのhashも一致させる。会話本文や生の画面XMLは結果に保存しない。確認できなければ`pass:false`で終わり、自動再送しない。
5. 同じコミットに対する合成検査を行い、`browser.json`・`android.json`・`production.json`を同じ結果フォルダーへそろえる。検査対象ソースのhash・コミット・実行日時が一致しなければ再検査が必要。24時間を超えた結果は受け付けない。

公開前の確認（GitHubを変更しない）:

```sh
node .github/scripts/magi-release-gate.mjs --commit <full-sha> --apk <signed.apk> --reference <previous-public.apk> --build-tools <sdk-build-tools> --reports workers/.wrangler/magi-chat-gate
```

公開は同じ引数に次を加える。タグは先に同じコミットへ作り、版番号・履歴とWorker→画面→履歴の既存の公開順も守る。

```sh
--publish --validation-run <successful-push-run-id> --notes <release-notes.md>
```

ゲートは同じSHAの指定workflow成功もGitHubへ照会する。配布APKは旧配布より大きいversionCodeと同じ署名を必要とする。既存Releaseの上書きはしない。アップロード後のダウンロード照合が失敗した場合はdraftのまま止まる。

実APIの費用が不明・予算が無い・端末が無い場合は、本番確認を未実施として配布を止める。合成結果から本番成功の記録を作らない。

## 不具合発見時

- 公開前はゲートを通るまで公開しない。未実施の条件を成功と書かない。
- 配布済みAndroidが送信不能なら、該当Releaseをdraftへ戻して新規ダウンロードを止め、影響する版と条件を記録する。インストール済み端末へ修正版が自動反映されるとは扱わない。
- Pages/Workerを戻す必要があるときは、直前の確認済みデプロイをCloudflareで選んで戻し、旧APKとの互換性も確認する。DB変更を推測で巻き戻さない。
- 修正後も同じゲートを通す。別の未確認APKで配布ファイルだけを差し替えない。

仕組みの参考: [Cloudflare Pagesのビルドと環境変数](https://developers.cloudflare.com/pages/configuration/build-configuration/)、[GitHub Actionsの実行結果API](https://docs.github.com/en/rest/actions/workflow-runs)、[Android Emulator runner](https://github.com/ReactiveCircus/android-emulator-runner)。
