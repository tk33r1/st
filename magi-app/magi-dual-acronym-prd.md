# PRD: MAGI デュアル・アクロニム UI

案（2026-11-02）。未実装。演出は本案の推奨であり、実装時に画面上で評価する。

## 1. 目的と二つの定義

既存の表示 `Multi-Agent Generative Intelligence` を A 面の表記に変更し、B 面を加える。同じ MAGI を「工学」と「芸術」の両方から読めるようにし、その二面性を美しい UI で示す。

| 面 | 表示する定義 | この作品での意味 |
| --- | --- | --- |
| A / SYSTEM | **Multiple Agents Generating Intelligence** | 複数のエージェントによって知性を生成する仕組み |
| B / ART | **Modern Art Generating Interiority** | 芸術として、人間の矛盾や葛藤を含む内面性を立ち上げようとする試み |

両面の頭文字はともに **M・A・G・I**。見出し **MAGI は単色のまま静止**させ、その下のサブタイトルだけで二面性を表現する。共通の現在分詞 **Generating** を固定した軸とし、前後の語句を対で切り替える。

二つは同じ MAGI の異なる読みである。切り替えによって回答モードや人格が変わったように見せない。ライト／ダークテーマとも連動させず、どちらのテーマでも両面を見せる。

### 1.1 言葉の扱い

- 綴りは **Interiority**。人の内面性・内的な経験を表す語として用いる。`Interiory` は採用しない（[Cambridge Dictionary](https://dictionary.cambridge.org/us/dictionary/english/interiority)）。
- `Multiple Agents Generating Intelligence` と `Modern Art Generating Interiority` は、名詞句に現在分詞の `Generating ...` を続けた見出し用のフレーズとして採用する。意味はそれぞれ「知性を生み出す複数のエージェント」「内面性を生み出す芸術」。
- `Generating` は前半の名詞の単数・複数にかかわらず同じ形で使えるため、両面で共通の軸を完全に固定できる。生成が進行する響きも、内面を立ち上げようとする本作の試みに重ねる。
- `Modern Art` は美術史上の近代美術を指す場合があり、`Contemporary Art` と同義ではない（[MoMA: Modern art](https://www.moma.org/collection/terms/modern-art)）。本作では M・A の頭文字と芸術的な読みを持たせる作品上の命名として採用し、日本語説明は「芸術としての試み」とする。
- `Generating Interiority` は作品の問い・制作意図として説明する。意識や人間の内面を実際に獲得・完全再現したという機能保証にはしない。
- 両面は同じ強さで扱う。B 面を故障、隠しエラー、悪性の裏人格のように演出しない。画面に `Surface` / `Ghost` の区分は出さない。

## 3. 成功条件

1. 二つの完成フレーズを読んだ人が、同じ MAGI に工学面と芸術面があることを説明できる。
2. 静止した MAGI の見出しの下で二つの意味が移り変わり、切り替え中も共通の Generating を視覚的に追える。
3. 切り替え中も、軸・周囲のボタン・スプラッシュ全体の位置が動かない。
4. 自動切り替えを待たずに両方の意味を確認でき、読んでいる面に止められる。
5. チャットへの入力・送信を妨げず、演出が処理中表示や回答モードの変更に見えない。

## 4. 推奨する演出

### 4.1 固定した軸を挟むクロスフェード

`Multiple Agents` と `Intelligence`、`Modern Art` と `Interiority` をそれぞれ一組として、同じタイミングでゆっくりクロスフェードさせる。中央の `Generating` は位置・色・明るさを保ち、アニメーションの対象に含めない。MAGI の見出し全体も静止させ、二面性の演出はサブタイトル内に収める。

各スロットの同じ位置に二つの完成語句を重ね、opacity だけを動かす。消去、タイプ入力、上下移動、拡大縮小、ぼかし、ランダム文字、点滅は加えない。遷移中は重なりが一時的に見えてよいが、静止時には片方だけを明瞭に表示する。

同じ器に二つの意味が宿ることを見せるための演出とする。速さ・派手さより、完成フレーズを読む時間と、左右が一緒に変化することを優先する。

### 4.2 比較した案

| 案 | 狙いへの適合と判断 |
| --- | --- |
| 消去してタイピング | ターミナルの質感には合う。ただしフレーズが未完成になる時間があり、別の定義への訂正・上書きにも見える。比較候補として残し、初期実装には採用しない |
| 二つのフレーズを常時二段で表示 | 二面性は最も確実に伝わるが、小さなスプラッシュでは説明文が増え、共通の軸の印象が弱まる。FAQ では両文をこの方式で併記する |
| 軸固定のクロスフェード | 完成語句を保ち、共通部分と差分を示せる。今回の推奨案 |

## 5. レイアウトと配色

### 5.1 見出しと三つのスロット

見出しの `MAGI` は全体を既存のアクセント色で統一し、静止した名前として置く。文字単位の色分け・強調・アニメーションは追加しない。A 面と B 面の切り替えでも位置・色・明るさを保つ。テーマ変更時は既存のテーマ色に従い、読み上げは「MAGI」の一語として扱う。

| Prefix | Pivot | Suffix |
| --- | --- | --- |
| Multiple Agents / Modern Art | Generating | Intelligence / Interiority |

- Prefix と Suffix は両方の語句を同じ Grid セルに置いたまま最大の幅を確保する。非表示の面も寸法計算に参加させ、切り替えで `display: none` にしない。
- 三列の列幅を内容の最大幅で決め、中央寄せする。Prefix は右寄せ、Suffix は左寄せとし、軸との間隔をそろえる。各語句は折り返さない。
- A 面の `Multiple Agents` の幅と、共通の `Generating` の幅を含めて再計測する。旧表記の幅を流用せず、letter-spacing、太字、実際のフォントを含めて最大幅を確保する。
  目安として、最大の組み合わせは 39 文字（旧表記は 35 文字）で、等幅・letter-spacing 0.12em ならトップページの 10px で約 280px、アプリの 11px で約 310px になる。320 CSS px の画面では、アプリ側は三段表示になる見込み。
- 一行が収まらない狭幅では、コンテナ幅に応じて Prefix / Pivot / Suffix の三段表示にする。両面とも同じ構造とし、遷移中の高さを固定する。極端な文字縮小や省略はしない。
- 狭幅の判定は画面幅だけに依存させず、リサイズ可能な MAGI ドックの内側の利用可能幅を基準にする。

### 5.2 配色

| 対象 | CSS 変数 | ライトの現行値 | ダークの現行値 |
| --- | --- | --- | --- |
| 定義の Prefix / Suffix | `--text-color` | `#1f2937`（濃いグレー） | `#d4d4d4`（柔らかい白） |
| 見出しの MAGI 全体、定義の Generating | `--primary-color` | `#15803d`（深い緑） | `#4ade80`（明るい緑） |

- 値の正本は両画面の既存テーマ変数。表は改訂時点の参考値であり、演出用の CSS に色コードを重複して直書きしない。
- MAGI は全体を一色で保ち、サブタイトル内では Generating だけにアクセント色を使う。両面とも同じ配色とし、芸術面だけ別色へ変えない。
- 静止中の前後の語句は両面同じ不透明度で明瞭に表示する。B 面だけを薄くしない。
- 既存の等幅フォントを使う。サブタイトルはまず発光なしで成立させ、必要な場合だけダーク側の Generating へごく弱い静的な発光を加える。ライト側では発光を付けず、MAGI の見出しへ新たな発光演出は追加しない。
- 発光を加えるなら既存の色変数で完結させる。未定義の `--primary-rgb` を参照しない。
- 両テーマで文字のコントラストと選択状態を確認する。フォーカス枠・現在面の区別は色や発光だけに依存させない。

### 5.3 操作部

- フレーズ全体を次の面へ切り替える `button type="button"` とする。見た目はサブタイトルとして配置し、既定の背景・枠・フォントは明示的に調整する。
- 近くに小さな `SYSTEM / ART` の状態表示を置き、両方の読みと切り替え操作があることを示す。現在面は下線などでも示す。
- 独立した「自動切替を停止／再開」ボタンを添える。押せる領域は WCAG 2.2 の AA（2.5.8）に合わせて最低 24 × 24 CSS px とし、隣の操作との間隔を取る。小さな `ver` ボタンと並ぶスプラッシュで、この部品だけを大きくしない。フレーズのボタンと重ねず、ボタンを入れ子にしない。
- 代案として、`SYSTEM / ART` の表示そのものを面を直接選ぶ二つのボタン（`aria-pressed`。押すとその面で静止）にし、部品の数を減らす構成も本人の評価で比べる。
- 版番号・人格ボタンの役割と操作は保つ。意味説明は「MAGIについて」の FAQ に置く。

## 6. 遷移と操作の契約

### 6.1 自動切替

1. 初期表示は A 面の完成フレーズとする。
2. A 面を 6000ms 静止表示し、700ms で B 面へクロスフェードする。
3. B 面の完成後に 6000ms 静止表示し、700ms で A 面へ戻る。
4. スプラッシュが見えていて、自動切替が有効な間だけ繰り返す。

時間は初期値とし、両画面の描画で読みやすさを評価する。左右は一つの進行度を共有し、異なる面の Prefix と Suffix が完成状態で組み合わさらないようにする。

### 6.2 手動操作と停止

- フレーズのクリック／タップ、フォーカス中の Enter／Space で反対面へ切り替える。同時に自動切替を停止し、選んだ面を読み続けられるようにする。
- 遷移中の追加の切り替え入力は受け付けず、予約もしない。完了後に次の操作を受け付け、フォーカスは保つ。700ms の間の入力が効かないことで反応が鈍く見えると評価された場合は、遷移を途中から逆向きに戻す方式と比べる。
- 自動切替の停止を押したときは、遷移中なら遷移先を即時に完成表示して静止する。再開は明示操作だけで行い、現在面を 6000ms 表示してから次へ進む。
- キーボードフォーカスが操作部に入ったときも自動切替を停止する。離れたことだけを理由に再開しない（WAI-ARIA APG の carousel パターンと同じ）。Tab で通り過ぎただけでも停止したままになることは、この仕様として受け入れる。再開ボタンを押した場合は明示操作を優先し、フォーカスが同じボタンに残っていても再開できるようにする。
- マウスを操作部に乗せている間は一時停止し、離れたら現在面の 6000ms を数え直して再開する（停止中・遷移中の扱いは上記に従い、手動で停止しているときは再開しない）。タッチ端末では起きない。
- 停止の選択は同じページの滞在中は保ち、言語変更・ドック開閉・新規会話で解除しない。DOM を再生成する場合、初期面は A に戻してよい。端末への永続保存は追加しない。

### 6.3 動きを減らす設定

- `prefers-reduced-motion: reduce` の場合は自動切替とフェードを無効にする。初期表示は A 面、手動操作では反対の完成フレーズを即時表示する。
- 同設定の間は自動切替を再開できない状態とし、理由を操作部の説明で伝える。
- 実行中に reduce へ変わった場合も、遷移先を即時表示して停止する。設定が戻っても勝手に再開しない。

## 7. アクセシビリティ

- 操作要素はネイティブの button とし、Tab・Enter・Space と視認できるフォーカス枠に対応する。
- 視覚演出の語句は `aria-hidden="true"` のラッパー内に置く。外側の操作ボタン自体は隠さない。
- フレーズのボタンには、現在の完成フレーズと「もう一つの意味へ切り替える」という操作目的を含む名前を付ける。名前は完成面の確定時だけ更新し、アニメーションの進行には連動させない。
- 名前は `aria-label` の一つの文字列にせず、`aria-labelledby` で視覚的に隠した二つの span を指して組み立てる。英語の定義の span に `lang="en"`、操作目的の span に UI 言語を付け、どちらの言語も正しい読みで読ませる。
- 両方の完成フレーズと短い意味説明を静的なテキストとして用意し、フレーズのボタンから `aria-describedby` で参照する。FAQ にも二つのフレーズを常時併記し、操作せず読める経路を作る。
- 英文の定義には `lang="en"` を付ける。操作名・停止／再開・意味説明は既存の日英切り替えに対応する。
- 定義の切り替えを `aria-live` にしない。チャット回答用の既存の読み上げ領域にも流さない。
- 停止はフォーカスを外した後も効くものとする。動きを減らす設定への対応だけを停止手段の代わりにしない（[W3C: Pause, Stop, Hide](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide)）。

## 8. ライフサイクルと実装制約

### 8.1 生成・停止・破棄

- 制御器は各ページに一つだけ置く（スプラッシュは同時に一つしか存在しない）。`agentHintHTML()` は HTML の生成だけを行い、呼び出しでタイマーやイベントを登録しない。
- 現行のスプラッシュは `agentLog.innerHTML = agentHintHTML()` の代入で作られ、代入箇所が両クライアントに散らばっている（改訂時点でトップページ4か所、`app.js` 2か所）。各箇所に後始末を足すと漏れが出るため、次の二つで寿命を閉じる。
  - 代入を `renderAgentSplash()` のような関数一つにまとめ、その中で DOM 挿入後に制御器を付ける。付けるときは前のスプラッシュの分を必ず破棄する。
  - 制御器はタイマーが動くたびに対象要素の `isConnected` を確かめ、DOM から外れていればタイマー・アニメーション・リスナーを破棄して自ら止まる。送信、履歴表示、一時チャットへの変更、リセット、言語変更などの置換は、これで漏れなく拾う。
- 古い非同期処理は世代識別または破棄済みフラグで無効にし、再生成後の DOM を書き換えない。開閉・再生成を繰り返しても制御器を増やさない。
- `document.hidden`（タブ切替・画面最小化を含む）、ドック閉鎖、スプラッシュが DOM から外れた状態では待機タイマーとアニメーションを止める。ドック閉鎖（幅0・画面外への移動）は IntersectionObserver で検出する。そのためスクロール領域外でも止まるが、これは副次的な挙動で要件ではない。別パネルに覆われた状態は IntersectionObserver では判定できず、6 秒ごとの opacity 切替は負荷も小さいため、停止条件に含めない。
- Android は既存のアプリ状態通知とも整合させ、バックグラウンド中に更新を続けない。
- 一時的に見えなくなる際は、遷移中なら遷移先の完成面に確定して停止する。再表示時はその面を 6000ms 表示してから再開し、経過分をまとめて実行しない。手動停止中は再開しない。

### 8.2 自給自足と機能分離

- ルート `index.html` は CSS・JS をインラインに置き、tk.st 以外でも外部取得なしに動かす。ライブラリ、CDN、追加の通信、フォントは導入しない。
- アプリ側は既存の `www/app.js` と `www/index.html` 内に置く。演出のための Worker・生成 AI 呼び出しは行わない。
- 静止時間にフレームごとの更新を回さない。遷移完了待ちもキャンセル可能にし、破棄後に処理を継続させない。
- 初期化に失敗した場合は A 面の完成フレーズを残す。入力・送信、人格説明、版情報、履歴表示の利用を妨げない。

## 9. 静的な意味説明

「MAGIについて」の「MAGIとは？」に、既存の由来の説明と並べて二つの英文と次の説明を置く。更新履歴は変更の記録として使い、意味説明の唯一の置き場所にはしない。

> MAGIには、二つの読みがあります。複数のエージェントが知性を生成する仕組みとしての「Multiple Agents Generating Intelligence」。そして、矛盾や葛藤を含む人間の内面を、芸術として立ち上げようとする「Modern Art Generating Interiority」。どちらも、同じMAGIを表しています。

英語版にも同じ内容を用意する。工学面の補足では、現在の事実回答などの経路を踏まえ、すべての回答が必ず三人格の合議を通るとは説明しない。

| 停止 | 停止後はフォーカスを外しても静止し、明示的に再開できる。再生成でも停止の選択が保たれる |
| 動きを減らす設定 | 初期・実行中の設定変更のどちらでも自動切替がなく、手動では完成フレーズが即時切り替わる |
| 読み上げ | 操作名・両定義・説明を確認でき、自動遷移を繰り返し通知しない。MAGI を一語として読める。回答の読み上げへ混入しない |
| 寿命 | 言語変更・送信・新規会話・履歴表示・一時チャットとの往復・ドック開閉後も、残存処理・二重タイマー・例外がない |
| 非表示 | タブ切替・最小化・ドック閉鎖・DOM からの除去・Android のバックグラウンド時に停止し、復帰時に高速で追いつこうとしない |
| 一時停止 | マウスを乗せている間は切り替わらず、離れると現在面を 6000ms 表示してから進む。手動停止中は離れても再開しない |
| 回帰 | 版情報、人格説明、FAQ、通常／一時チャット、保存復元、入力・送信が既存どおり動く |
| 自給自足 | ルートを tk.st 以外で開いても表示・切り替えが動き、追加の外部通信が発生しない |

構文チェックに加え、タイマーの重複・破棄・対の維持は合成検査で確認する。位置・読みやすさ・美しさは実際の描画と操作で確認する。確認できない環境は未確認として記録する。

### 10.2 美しさの評価

完成フレーズと遷移の画面を並べ、次を本人が評価する。時間指定や構文チェックだけで見た目を合格としない。

- 同じ MAGI の二面性に見えるか。単なる広告文のローテーションに見えないか。
- 静止した MAGI の下で二つの意味が移り変わる構成が明確か。Generating が自然な軸となり、前後の余白が不自然に空かないか。
- B 面も A 面と同じ程度に読めて、工学と芸術の違いが伝わるか。
- エンブレム・人格ボタンと一緒に見て、装飾や操作部が多すぎないか。
- 演出が入力したくなるタイミングを妨げないか。

弱ければ静止時間・余白・操作表示を調整する。それでも二面性が伝わらなければ、二つのフレーズの常時併記案と比較して演出を再選定する。

### 10.3 公開

- 見た目の変更にも既存の [MAGI の公開前検査](公開前検査.md) を適用する。手元の演出確認で代替しない。
- Pages の公開には、対象 SHA の会話契約検査と `magi-chat-validation.yml` の成功を必要とする。
- Android の配布は同文書の最終署名 APK・同一ソースの合成検査・本番疎通・公開ゲートに従う。未実施の検査を合格とみなさない。
- 版番号・キャッシュ・更新履歴の整合と公開順はルート `AGENTS.md` に従う。実装時点で次の版を決め、本 PRD で先取りしない。

## 11. 実装順

1. 両クライアントの通常スプラッシュで単色の MAGI 見出しを維持し、その下へ三スロット・操作部・静的な説明を追加する。
2. まず静止した両面を確認し、幅・余白・配色・狭幅・操作・読み上げを成立させる。
3. 同じ契約の制御器を両クライアントへ実装し、既存の生成・置換・非表示・破棄の経路へ接続する。
4. クロスフェードと停止／再開を追加し、受け入れ確認と本人による見た目の評価を行う。
5. 必須の公開前検査を通し、既存のリリース手順に従って公開する。
