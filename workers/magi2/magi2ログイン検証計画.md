# tk.st / MAGI ログイン検証計画

計画案（2026-10-25、2026-10-26 改訂）。未実施。対象仕様は [設計書](magi2ログイン設計書.md)。本書の作成・文書検査はログイン機能の実装完了や試験合格を意味しない。
実装・公開後は冒頭を「実装済み（日付）。正本はコード」に変更し、以後は更新しない。実施結果は別の公開評価・実装記録へ残す。

## 1. 検証原則と段階

- 対象は magi2 と新設の accounts（`tk.st/user/*`・`account.tk.st`）。SAFE TOOLS などほかの区画は、ログインを足していないこと・変わっていないことだけを確かめる。
- 本人 A/B と guest を分け、他人のデータを読む/書く/消す経路がないことを最優先にする。
- L0（成立性）、L0.5（端末内の保存の強化）、L1（認証・枠・隔離・退会・管理画面）、L1.5（パスキー管理）、L2（設定同期）、L3（履歴同期）、L4（添付）の合格を分ける。後段未実施を初期公開の失敗にせず、後段を利用可能とも表示しない。
- 未確認、未設定、対象外、失敗を区別する。trial 中だけの成功、模擬パスキー、Chromium だけの成功を Free 本番・Android/iOS の合格へ読み替えない。
- 模擬 issuer/JWKS/token endpoint、模擬 AI/音声、ローカル D1 を先に使う。外部 AI を呼ばずに認証・保存・ストリームの検証を完了できる構成とする。
- 実 Auth0/Resend/実機の試験は合成アカウント・宛先を用いる。実運用者の履歴・インストール済み本番 APK のデータを消さない。Android は別 applicationId の試験ビルドを使う。

## 2. 環境・初期データ・証跡

| 層 | 環境・初期データ |
| --- | --- |
| Worker | Node 24、既存 Worker 検証方式、Wrangler ローカル D1 と実 Service Binding のローカル確認。模擬 OIDC 署名鍵を複数用意。accounts は `tk.st` と `account.tk.st` の2つのホストを模擬する |
| Web | トップと `account.tk.st`、PWA を Chromium/Firefox、狭幅/通常幅、日英・ライト/ダークで確認 |
| モバイル Web | Android Chrome/PWA、iOS Safari/ホーム追加 PWA。Cookie 分離も含めそれぞれ独立確認 |
| Android | Capacitor 8、署名済み試験 APK。Android 13/14/16 を代表候補とし、実際に試した OS・機種・WebView/Chrome 版を記録。未保有端末は未実施とする |
| 互換 | 現在配布中の APK の版/hash、旧 Web/PWA キャッシュ、新画面＋旧 Worker、新 Worker＋旧画面 |
| Auth0 | 本番とは隔離した評価設定。Free/trial 状態、client 型（3つ）、許可 callback、connection、RP ID、期限、email provider を記録 |

guest 履歴 G、アカウント A の履歴/設定/未送信文/画像/保留回答、B の別内容を準備する。本文・タイトル・指示・画像に別々の合成マーカーを入れる。重複メール、同じ会話 ID、旧形式、壊れた JSON、保存容量不足も用意する。L0.5 用に、localStorage だけに保存した旧形式の会話（件数・大きさの異なる複数組）と、書き出しファイルの正常・壊れた・未知の版・上限超過の組を用意する。

証跡は commit、dirty 差分一覧、設計採用値、画面/Worker/APK の版と hash、環境、要求結果、DB/ファイル/通信の許可済み差分を含める。D1 全 SQL とバインド引数、保存アダプター、Service Worker/Cache API、WS フレームとネイティブ pending を開始前から監視する。削除後の件数一致だけで「保存しなかった」と判定しない。

生の HAR、token、メール、署名鍵、D1 dump は Git 無視の `workers/.wrangler/` 等に隔離し、公開記録には載せない。診断の失敗時出力にも token を出さない。

### 3.1 L0.5：端末内の保存の強化

| ID | 操作・条件 | 合格条件・証跡 |
| --- | --- | --- |
| E-01 | 会話の保存・設定画面を開く操作の後に `persist()` を呼ぶ。読み込み直後、許可/不許可/非対応のブラウザ | 利用者の操作の後に1回だけ呼ぶ。結果を設定画面に表示し、不許可では書き出しを勧める。iOS Safari（非ホーム画面）でホーム画面への追加を案内 |
| E-02 | localStorage の旧形式の会話を IndexedDB へ移す。途中でタブを閉じる・容量不足・IndexedDB 不可（プライベートモード）・新画面2タブ同時 | 読み戻しと原本再取得で照合。移行を理由に原本を自動削除しない。途中失敗で原本/会話消失0、次回に冪等再試行。排他や保存先が使えない環境は既存保存のまま動く |
| E-03 | 書き出し→別ブラウザで読み込み、同じ会話 ID の新旧、壊れた・未知の版・上限超過のファイル | 正常は全会話・設定を復元。同じ ID は新しい方を残し上書き前に確認。異常ファイルは何も変えずに拒否 |
| E-04 | 一時チャット・画像付き会話を含めて書き出す | 一時チャットは含まれない。添付の対象外が一覧に示される。所有者の内部 ID が書かれない |
| E-05 | 全操作の通信を監視。トップを tk.st 以外（インスクリプション相当）で起動 | サーバー・外部への送信0、外部資産の読込0。tk.st 以外でも同じ機能が動く |
| E-06 | Android の書き出しファイルを Web で読み込み、その逆 | 共通 schema で相互に復元できる。未対応の項目は欠落を明示する |
| E-07 | ロックに参加しない旧版タブを開き、新画面のコピー・照合・切替の各直前/直後、背景化中に旧版から会話を保存。新画面の保存も並行。旧版が古い内容を含む配列全体を繰り返し書き戻す | 原本は消えず、イベントと復帰時の再取得で旧版の追加を取り込む。新画面のデータを旧snapshotで置換しない。取り込み済みの会話の古い内容は再取込み・競合0。未取込みの同IDの異なる内容は両候補を保全。ロック取得/一定時間の無通信を旧タブ不在と判定しない |
| E-08 | 互換原本保持中に容量不足、切替後のIndexedDB障害、新画面で個別削除、端末履歴の明示削除、L1ではlogout。終了・再起動と旧snapshot再読込も実施 | 容量不足では原本を維持し移行を保留。障害時に古い原本で上書きしない。個別削除は互換原本からも当該会話が消え、旧タブの書き戻し後も再取得で取り除かれ、tombstoneで復活を防止。全削除/logoutは当該ownerの互換コピー/journalも対象にし、削除世代の印で自動復活を防ぐ。アカウントlogoutでguest原本を消さない |

## 4. L1：認証と権限

### 4.1 Web / OIDC / Native token

| ID | 条件 | 合格条件 |
| --- | --- | --- |
| A-01 | Cookie・CSRFのない初回表示からsession取得→login POST→Auth0→callback→session再取得（両ホスト各々）、同時に2タブで開始 | 初回bootから成功。transaction・ホスト・ブラウザを照合し一度だけ消費。正しい戻り先・本人・新session ID。匿名CSRFは認証後の操作に流用不可 |
| A-02 | state/nonce/verifier 欠落・不一致・5分超過、二重 callback、別ブラウザから callback、tk.st の transaction を account.tk.st の callback へ | セッション作成0、user 作成0。エラーを安全に表示しゲストへ自動降格しない |
| A-03 | 戻り先に外部 URL、`//host`、エンコード/制御文字、callback 自身、もう一方のホストを指定 | 固定許可先だけへ移動。open redirect・認可 code の外部転送なし |
| A-04 | JWT の署名改変、none/想定外 alg、issuer/aud/azp/scope 不一致、期限切れ/未来 nbf、ID token の流用 | 401/403。設定・履歴・AI・利用枠の更新なし。外部入力の鍵 URL を取得しない |
| A-05 | 固定 issuer の鍵 rotation、未知 kid の連打、JWKS 障害 | 既知鍵・期限内 token のみ継続。再取得の制限。検証不能時に成功扱いしない |
| A-06 | メール未確認、userinfo と token の sub 不一致、同じメールで別 sub | bootstrap を拒否/別 ID として扱い、メールで統合しない。一般 API から user を自動作成しない |
| A-07 | 任意 Origin、CLIENT_API_KEY、偽 X-User-ID、Cookie+Bearer 同時、存在しない/blocked/deleting user | 認証専用 API を通れない。渡した user ID で権限が変わらない |
| A-08 | Auth0 更新・accounts Service Binding・D1 を個別に停止。account指定でCookie/Bearerを欠落、guest指定で資格情報を付ける | 認証付き処理は503/401、guest への自動再送なし。モード衝突を拒否。真の無認証 guest は既存枠で継続 |
| A-09 | foreign Origin、CSRF 欠落/不一致、Cookie だけで通常の更新/削除/送信。session初期化とcallbackは5.4の別契約で試す | 通常の更新APIは拒否。GETで本人データ変更/AI呼出しなし（初期化Cookieと認証callbackのセッション確立は別）。正規のCSRF付き操作だけ成功 |
| A-10 | 両ホストの session Cookie を検査し、ログイン前に固定 ID を注入 | `__Host-`/Secure/HttpOnly/Path=/、Domain なし、tk.st は Lax・account.tk.st は Strict。ログイン後 ID が更新され固定化なし。互いのホストへ届かない |
| A-11 | Web/Native の期限境界・refresh 同時実行・ローテーション再利用 | 期限を延ばし放題にしない。更新は直列化/lease、失効した family を使い続けない。AI 要求の二重送信なし |
| A-12 | 危険な操作（書き出し・データ削除・退会・一括終了）に、5分超の auth_time、別 sub、二重 intent、Native の ID token や Bearer を渡す | account.tk.st の新鮮な対話認証だけを受理。Native の資格情報では受け付けない。クライアント自己申告の時刻を信用しない |
| A-13 | tk.stから管理のsession/通常APIへfetch（credentials付き）・フォームPOST・iframe・window.open後の操作。callbackには有効なtransactionを付けずに要求 | 通常APIのsame-site/Origin不一致/CSRF欠落、callbackのtransaction不正を拒否。個人データ読取/管理操作0。管理画面へのリンク表示と正規Auth0 callbackは許可し、ページ遷移まで拒否しない |
| A-14 | tk.st から `Domain=tk.st` の Cookie（同名・`__Host-` 風の名前・大量）を設定して account.tk.st を操作 | 管理 API は自分の `__Host-` Cookie だけを読み、詰め込まれた Cookie で本人・CSRF・セッションが変わらない |
| A-15 | account.tk.st の無操作30分・絶対12時間の境界、危険な操作の5分境界、tk.st のログアウトと account.tk.st のログアウト | 期限どおりに失効。危険な操作は期限切れで再認証を求める。一方のログアウトがもう一方に波及しない |
| A-16 | tk.st/user/api に export・data-deletion・delete・revoke-all・passkeys を要求 | 存在しない（404）。tk.st の Cookie では管理操作ができない |
| A-17 | 初回ログイン（tk.st・account.tk.st・Native）、規約の版を上げた後の要求、同意を拒否 | 初回は同意記録と内部ID作成を原子的に行い、拒否でuserを作らない。既存利用者はterms_requiredとなり、再同意まで通常利用/新規同期を拒否。5.6の終了用操作は維持 |
| A-18 | 管理画面からOriginなしの同一オリジンGETでsession取得、正規CSRFヘッダー付きのキー一覧、既定モードのfetchでの更新POST。Referrer-Policyの実値、Origin不一致、null、Fetch Metadata欠落、匿名CSRFの通常API流用 | Origin省略の正常GETだけ成功し、sessionにCSRFを先に要求しない。管理画面は`same-origin`で、正規の更新POSTに完全一致のOriginが付き成功する。通常APIのFetch Metadata欠落/不正Originや匿名CSRF流用は拒否。ログイン前は本人情報を返さない |
| A-19 | 管理画面からAuth0への対話認証とパスキー管理認証を往復。callbackのOrigin省略/null・same-siteと、不正/消費済state、transaction Cookie欠落、別host/client/purpose/subを試す | 正規の遷移は通常APIのOrigin/CSRF条件で拒否せず、OIDC/ブラウザ結び付けで検証。不正はセッション/キー変更0、正常はクエリなしへ303。L1.5部分は同段階で実施 |
| A-20 | 旧規約に同意済みのAが新版を拒否し、再ログイン・token更新・同期停止・書出し・削除・退会・進捗確認・一括終了を行う。別試行で新版に同意 | 同意なしでも5.6の許可操作だけ成功し、再認証/CSRF/host検査を省略しない。退会後の進捗はboot CSRFと専用tokenを検査し、IDだけ・別人のtokenを拒否。同期on・チャット・設定変更は拒否し、明示同意後だけ通常利用を再開 |

| N-05 | Android から管理（書き出し・退会）を開く | システムブラウザで account.tk.st を開き、Web として対話ログインする。Native token・セッションの受け渡し0 |

## 5. L1：通信・利用枠・回帰

| ID | 条件 | 合格条件 |

## 10. 実行順・費用・リリース判定

1. 設計 G01〜G07 の当該段階分を確定し、期待値/期限/採用依存を固定する。
2. L0.5 はローカルと Playwright で E を実施し、ログインと独立に公開判定する。
3. ローカルで A/T/Q/S/D と模擬パスキーを実施。D1の原子性とService BindingはWranglerの実経路でも確認する。account.tk.st の分離（A-13〜A-16）は2つのホストを実際に分けた構成で行う。
4. PlaywrightでWeb/PWAの操作・隔離・通信・SWを確認。構文検査は変更した全JSとHTML内scriptを対象にする。
5. 実Auth0/ResendでF/PとSSO省略を確認。Freeの実証ができない項目は公開ゲート未達のままにする。
6. Android実機とiOS Safari/PWA、旧APK、旧SWの互換を確認。未確認機種・経路を結果表へ残す。
7. 当該段階の削除/停止/ロールバック演習後、Worker先行で公開。合成アカウントによる最小の本番確認を行う。

文書作成時に試験スクリプト・Auth0設定・migrationは存在しない。実装時は既存の `.github/scripts/test-magi2.mjs` と各ブラウザ/native検証へ接続し、accounts用検証を追加する。新規試験名・実行コマンドは作成後に実装記録へ記載し、予定コマンドを成功済みと書かない。Markdownだけの今回の変更にはAI API試験・全サイトビルドは不要。

Auth0/Resendのメール数とMAU/M2M、Workers/D1/R2を記録する。外部AI/音声は基本0回。実AIが必要なら既存予算台帳の残額と会社別上限を使い、送信前の予約を行う。文書作成を根拠に有料プランへ変更しない。
