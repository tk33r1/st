# サイト内検索 Phase 4 PRD

実装中（2026-10-12更新）。未公開。読み生成・共通照合・共通UIと通信APIの基盤を着手済み。実ページ・Worker・出荷ビルドへローカル接続し部分検証済み。60語・新scopeの実Jev／smoke・共通UIの入力速度・実adapterの7,500件準備とブラウザメモリを評価済み。準備は約2.7〜3.2秒へ短縮し、ChromiumのIME経路も確認した。初回入力と短い停止・Linux／実機と本番確認は残る。進捗は[実装記録](../.github/site-search/phase4/implementation-progress.md)。Phase 3 の公開済み資料は書き換えず、本書で Phase 4 の追加要件を定義する。

仕組みは[設計書](site-search-phase4-design.md)、作業順は[実装計画書](site-search-phase4-plan.md)、合否は[検証計画書](site-search-phase4-verification.md)。①はブラウザ内の文字・読み検索、②は Jev の意味検索、③は Shinya Takeda AI に聞く機能を指す。

## 1. 目的と現在の問題

1. 日本語の変換途中でも、探している語を含むページ・記事をサジェストする。
2. 404 の①をサイト全体の検索対象に揃え、DJ・Thoughtなども検索できるようにする。
3. 404 の「サイトの全体」を、ページ間の関係が分かり、そこから移動できるツリーにする。同じ階層では特定の区画を優遇しない。
4. tools/gameにもJevの意味検索②を追加し、404・日刊・tools・gameの検索ロジックとUIを共通部品へ統一する。違いは検索対象・検索フィールド・絞り込みなどの設定に閉じ込める。

2026-10-11 のコード確認では、404 の入力中の検索は `tools.json`・`game.json`・`glitch.json` の3一覧だけを使っている。DJ・Thoughtは `data/site-search.json` に載っているが、①はその索引を使わない。4区画の大きいカードと、小さい「ほかのページ」のリンクも役割に根拠のない見た目の差になっている。

日刊の①は題名・要約・要点・出典・カテゴリー・タグを文字照合する。読みの索引がなく、日刊ではひらがな・カタカナ・全半角の違いも十分に吸収していない。404 には既に全半角・かなの正規化があるが、漢字の読みと未完成のローマ字を扱う処理はない。

## 2. 対象

| 画面・データ | Phase 4 の対象 |
| --- | --- |
| 404 の検索①・サジェスト | 公開サイト全体の索引へ統一し、文字一致と読み一致を扱う |
| 404 の「サイトの全体」 | すべての掲載区画を同じ規則で描く、リンク付きの階層表示へ変更 |
| 日刊ニトリ・日刊リテールテックの横断検索①・サジェスト | 媒体ごとの全年度の記事に読み対応を追加。既存の絞り込みを適用 |
| ツール一覧・ゲーム一覧の検索①②・サジェスト | 読み対応とJev検索を追加し、404・日刊と同じ検索部品・操作・結果表示を使う。通常のカタログカードは検索欄の外に維持 |
| 通常の公開ページ | 404 の検索対象として、そのページの題名・説明などから読みを生成。各ページに検索欄を新設する意味ではない |

「全日本語」は、特定の例示語だけを手で登録する方式に限定せず、検索対象の日本語を辞書で解析することを意味する。辞書にない固有名詞や複数の読みの完全な解決を保証するものではない。

### 2.1 検索対象の文章

- 404：出荷する HTML から作る既存のサイト索引の `title`・`title_en`・`description`・`description_en`・`detail`・元の題名・タグ・カテゴリー・ジャンル。DJ・Thoughtのページ内の正式名称も `detail` から検索できる。既存3一覧の①が調べる全文の題名・説明・短い説明・タグ・ジャンルも保持する。Worker用索引の短縮された説明だけへ置き換えない。
- 日刊：現在①が調べる題名・要約・要点・出典・カテゴリー・タグ。`search_terms` は②の候補選び用で、今回①の言い換え語へ転用しない。
- ツール・ゲーム一覧：それぞれ現在①が調べる正本 JSON の項目を維持。
- ページの本文全文、JSが描くプロフィール・年表、外部ニュースの全文、PDFの内容は追加で取り込まない。これらは別の全文検索の要件になる。

### 2.2 掲載するページ

検索とツリーは同じ掲載規則を使う。既存の `site-search-index.py` の公開範囲・noindex・転送・canonical の除外を維持する。404 の常設入口であるお問い合わせなどの既存の明示例外は維持する。

DJの公開プロフィールと曲リクエストは対象。noindex で運用上隠しているブース・日程調整、記念日ページ、Worker・API・ソース・設計書・非公開ファイルは、自動的に掲載しない。「全ページ」は、検索・案内に掲載する公開ページ全体を指す。

日刊のポータルと号ページの題名・説明は404の①から探せる。個々の記事の内容は、各媒体の全年度検索へ渡す。404 が毎回2誌の全記事索引を取得する構成にはしない。404の②が号ページを除く現在の範囲も維持する。

### 2.3 今回追加しないもの

ツール・ゲームと日刊の③、新しいAIプロバイダー、既存scopeの問い・閾値・回数上限の変更、ブラウザでの日本語辞書のダウンロード、トップページへの外部JS追加、フレームワークの導入。Workerへの`tools`・`game`のscope追加と、新scopeの候補・問い・閾値の評価は今回に含める。

## 3. 検索と入力の期待値

### 3.1 必須の途中入力

| 記事・ページ内の語 | その語の読みで候補に入る入力 |
| --- | --- |
| ニトリ | `ｎ`、`に`、`にｔ`、`にと`、`にとり`、`ニトリ`、`nitori` |
| 家電 | `ｋ`、`か`、`かｄ`、`かで`、`かでｎ`、`かでん`、`家電`、`kaden` |

途中入力でも最大6件のサジェストと該当件数を表示し、①の全候補一覧へ進める導線を付ける。この操作では②③を送信しない。1文字で6件を超える場合は、目的の記事が全候補一覧に含まれることまで確認する。完全な語では目的の記事・ページが上位へ来ることを評価する。

4画面の①の一覧は最初の100件を表示し、「さらに100件表示」で最後の候補まで開ける。100件で打ち切らず、大量のDOMを一度に作らない。追加表示で②③や検索語の計測を再送信しない。条件が変わったら表示件数を初期値へ戻す。tools/gameの通常カタログは残し、検索候補・結果には4画面共通の行表示を使う。

### 3.2 共通の規則

- 現在の文字の部分一致を維持し、読みの前方一致を加える。別表記から検索できる範囲が広がることは意図した機能変更。
- 全角英字・半角かな・ひらがな・カタカナ・大小文字を同じ正規化で吸収する。空白区切りの複数語は4画面ともレコード単位のANDで照合する。既存の全文連結・空白除去で得られる文字一致も共通部品内の互換照合で保持する。
- 読みの前方一致は語の先頭に当て、文章全体の先頭に限定しない。未完成の末尾子音を捨てない。
- ヘボン式・訓令式など通常のローマ字入力差、`n`/`nn`/`n'`、促音・拗音・長音を扱う。詳細は設計書3章。
- 入力欄の値は自動変換しない。読みは内部の照合だけで使う。カーソル・選択範囲・IME候補の操作を妨げない。
- IME変換中は候補を更新する。変換確定のEnterを検索実行にしない。変換中の上下キー・Enterをサジェストが奪わない。
- 読み対応は確定後の①にも適用する。サジェストで見えた候補が、同じ語の①から消える状態を作らない。
- 複数語のANDと既存文字一致の互換照合を共通実装し、カテゴリー・地域・月・ジャンルなどの絞り込みは①②の両方へ適用する。適用できる絞り込みだけをscope設定で宣言する。
- 4画面で①②の重複除去、結果数の表示、URL受け渡し、古い非同期応答の破棄を共通化する。受け渡された検索語は①へ反映するだけで、②は自動実行しない。

### 3.3 表示順と説明

①の既定順は4画面とも題名の完全一致→題名の文字前方一致→題名の文字部分一致→題名・タグの文字一致→題名・タグの読み一致→説明等の一致を基本とする。同点の安定順はscope設定で指定し、日刊は新しい記事を先にする。tools/gameのタイトル順・新しい順・古い順は共通の並べ替え操作の選択肢として残す。②はJevの確率順とし、①の並べ替えで上書きしない。

かな・ローマ字入力では、日本語の読み一致を、説明内のASCII1文字だけの偶然の一致より優先する。「完全一致」などの表示を読みの前方一致に誤って付けない。読みで見つかった件も①の候補数に数える。サジェストは4画面とも最大6件。

### 3.4 共通の検索UIとJev実行

4画面は1つの共通JSとCSSを使い、入力欄・検索ボタン・最大6件のサジェストと件数・「全候補を見る」・①「文字・読みで一致」・②「目的に近い候補」・状態表示・中止・追加表示・検索とプライバシーの説明を同じ構造、文言、余白、キーボード操作で描く。scopeによる対象名・filters・並べ替えの選択肢だけを設定で差し替え、画面ごとに別の検索フォームや状態機械を持たない。通常カタログ、日刊の本文、404のツリーは検索部品の外側に置く。③は404だけの既存の追加操作として接続し、①②の共通処理へ書き写さない。

入力中は①だけを更新し、Enterまたは検索ボタンで現在の条件の①を確定して②を1回実行する。IME確定Enter・語の受け渡し・filtersや並べ替えの変更・全候補表示・追加表示・自動復帰から②を送らない。変更後の②は古い結果として破棄し、次の検索実行を待つ。②が停止・上限・失敗でも①を継続する。②の判定対象数と不完全な応答を共通表示し、候補の一部の判定を検索対象全体の「該当なし」と表現しない。

検索対象は`site`（404の掲載ページ）、`nitori`・`retail`（媒体内の全年度の記事）、`tools`（公開ツール）、`game`（公開ゲーム）。tools/gameはブラウザで全サイトの②を受け取って後から絞る方式にせず、Workerでscopeとfiltersを適用してから候補を選びJevへ送る。新scopeの問い・閾値は評価で固定し、既存3scopeの公開済みの評価をそのまま合格記録にしない。

## 4. 404のサイト構造表示

「サイトの全体」は、ホームを根にして、URLの階層が分かる縦のツリーにする。次は構造例であり、件数・子ページを手で固定する正本ではない。

```text
tk.st / ホーム                         → /
├─ お問い合わせ                        → /contact/
├─ DJ                                  → /dj/
│  └─ 曲リクエスト                      → /dj/request/
├─ ゲーム                              → /game/
│  └─ 各ゲーム                         → 各ページ
├─ Glitch                              → /glitch/
│  └─ 各記事                           → 各ページ
├─ 職務                                → /job/
│  ├─ 日刊ニトリ                       → /job/nitoridaily/
│  │  └─ 年・月・各号                   → 各号
│  └─ 日刊リテールテック               → /job/retailtechdaily/
│     └─ 年・月・各号                   → 各号
├─ MAGI                                → /magi/
├─ Motovlog                            → /motovlog/
├─ Thought / 思索の余白                 → /thought/
└─ ツール                              → /tools/
   └─ 各ツール                         → 各ページ
```

- 同じ深さは同じ文字サイズ・太さ・行高・余白・リンク色にする。4区画だけカード・大見出し・アクセントで強調しない。「ほかのページ」という小さい別枠を廃止する。
- ページへのリンクと、子の開閉を別の操作にする。枝を開かずに親ページへ移動できる。
- 第一階層は初期表示ですべて見える。個別ページは折りたためる。件数は子のある枝に同じ形式で付ける。
- 日刊は職務の配下に置き、号は年・月でまとめる。年・月にページがなければリンクを作らない。
- URLの到着区画が分かる場合は、その枝を開いて場所を示す。検索語を理由に他の枝を消したり小さくしたりしない。
- 通常の公開ページを追加すると、索引生成とともに枝も追加される。日英の主要入口の名前は404の既存の入口定義を使う。
- 320px幅・文字拡大・キーボード・読み上げで階層とリンクが使える。装飾の罫線や記号を読み上げさせない。
- JavaScript無効・索引の取得失敗でも、公開時に作ったツリーから移動できる。

## 5. データ量・速度・失敗時

読みは語彙を共有し、各ページ・記事への対応を持つ。`n`・`ni`・`nit`等の全途中入力やローマ字の全組合せを保存しない。大きい辞書は公開前の処理でだけ使う。

| 項目 | 公開前の目標・条件 |
| --- | --- |
| サイトの読み索引 | 生JSON 512KiB以下、gzip換算128KiB以下（現在の掲載規模）。ツール・ゲーム一覧用の読みを含む追加分の合計 |
| 日刊の読み索引 | 1,000記事あたり生JSON 1MiB以下、gzip換算256KiB以下。固定ヘッダーは別記 |
| 照合と候補のDOM更新 | 10,000レコードの固定fixture、ChromiumのCPU4倍抑制で入力から更新までp95 50ms以下 |
| 新しい読み処理の出荷ビルドへの追加時間 | 固定10,000レコードで60秒以下。依存取得時間は別に測る |
| 初期表示 | 読みの取得・準備を待たず、文字検索と静的ツリーを使える |

数値は設計上の目標で、計測結果ではない。P4-T02で現行・大規模fixtureを固定し、超えた場合は圧縮・分割・実装を見直す。測定環境や範囲を変えて合格にしない。

読みの未取得・失敗・版ずれでは既存の文字検索を残す。対象0件にすり替えない。読みの準備中は「読み検索を準備中」、失敗時は「現在は文字一致のみ」を日英で示す。文字一致0件を、読み検索まで完了した「該当なし」と案内しない。準備完了時は現在の条件で候補を更新し、入力・フォーカスを動かさない。未解決の語は文字一致を維持し、読みの欠けを生成側の公開できる記録へ残す。生成時の依存・契約違反は公開前に検知し、壊れた新しい成果物を出さない。

基礎索引と読みの版、またはブラウザの基礎索引と②の応答の版が異なる場合は、検知時に基礎索引と読みを自動で1回だけ取り直す。404・日刊・tools/gameで同じ規則を使い、再試行ボタンや検索の確定操作を復帰の条件にしない。古いタブでも整合する組へ復帰できるようにする。復帰処理は同じ画面の初期化から再読み込みまで1回に制限し、同時の検知は処理を共有する。入力・絞り込み・追加表示・再取得後の不一致を理由に回数を戻したり、再取得を繰り返したりしない。復帰中も文字検索を使え、復帰できなければ検査済みの基礎索引による文字検索を続け、状態を案内する。版の異なる②の結果は採用せず、復帰処理から②③や検索語の計測を送信しない。

新入口のWorker側でも、generation不一致とソース混在を利用回数・Jev・判定結果キャッシュより前に確認する。旧snapshotを持つ場合は、要求の期限内で1回だけ固定ソースを再取得・検査する。同時の更新は共有し、再取得には間隔制限を設ける。一致すればその明示要求で②を続け、未解消なら利用回数とJevを使わず`index_updating`を返す。ブラウザはこの応答でも上記の1回だけの復帰を行い、②を自動再送しない。Worker側の契約の正本は設計書4.5。

## 6. 通信と互換性

- 入力中に検索語をWorker・外部APIへ送らない。読み用JSONの同一サイトからの取得には検索語を載せない。
- 読み・ローマ字・IMEの途中値を新しいアクセス解析イベントへ送らない。既存の検索語の伏せ字、変換中の計測抑制、解析停止を維持。
- tools/gameの一覧で②を明示実行したときだけ、検索語と検索条件をmagi2 Workerへ送り、Workerが公開候補の情報と検索語をTypeSafe AIへ送る。ブラウザからTypeSafe APIを直接呼ばず、キーを持たせない。
- 4画面の新UIは同一サイトの固定入口`POST /search/api/rank`を使い、magi2 Workerの既存②処理へ接続する。これにより`tools/index.html`のCSPを広げずに検索できる。検索語がWorker経由でTypeSafe AIへ渡ることは、一覧の注記・FAQ・構造化データへ明記する。個別のSAFE TOOLSのCSP・ファイル・入力内容・結果の非送信、Clarity禁止は維持する。一覧の検索と個別ツールの処理を区別して説明する。
- Workerが使う既存索引のフィールド・ハッシュ・日刊generationは読みの追加だけを理由に変えない。読みは別ファイルに持つ。新scopeと新画面契約の追加は既存クライアントに互換を保ち、共通経路の変更で既存②の評価結果が変わる場合はrevisionと再評価を必要とする。
- 古い404・日刊HTMLが新しい`assets/site-search.js`を取得しても、既存の`STSiteSearch.rank()`・`readResponse()`と描画・状態・計測の契約を維持する。新UIは別の描画なしの通信APIを使い、旧HTMLへ新しい共通UIの読み込みを要求しない。旧HTML＋新JSの回帰を公開条件に含める。
- 共通JS/CSSの版と、それを読むHTML・日刊テンプレート・全号の参照は同じ公開単位で更新する。再生成だけの号には `Date-Sync: skip` を使う。
