# サイト内検索 UI 改修 設計書

実装済み（2026-10-12）。正本はコード。公開は未実施。Phase 4 で公開した共通検索の**見た目と操作**を、一般的な検索サイト（Google・Amazon）と同じ形に改める。
照合・読み・②（Jev）の通信の契約・版ずれからの復帰・候補クリックの記録の送り先は Phase 4 のまま変えない。
本書は、Phase 4 の [PRD](site-search-phase4-prd.md) 3.1・3.4 と [設計書](site-search-phase4-design.md) 3.4 のうち UI の構造・文言・見た目を共通にするという決定と、PRD 3.2 の「受け渡された検索語は②を自動実行しない」の1つの例外（3.8）を置き換える。両文書は凍結済みのため直さない。

## 1. 目的と現在の問題

Phase 4 の UI は、仕組みの区分をそのまま画面に出している。機能は足りているが、使う人が初めて見て操作を推測できない。

| いまの表示 | 問題 |
| --- | --- |
| 入力欄の上の見出し「検索語」と、文字の「検索」ボタン | 一般的な検索欄は、欄の中に薄く「〇〇を検索」と書き、ボタンは虫眼鏡にする。見出しは要らない |
| 「入力中の候補」「① 文字・読みの一致」「② 意味の近い候補」が縦に同列で並ぶ | 候補（打っている途中の手がかり）と結果（確定した検索の答え）の区別がつかない。①②は作り手の区分で、使う人には1つの結果の一覧でよい |
| 「文字と読みで検索できます。」「20件から20件を選択、20件を判定」などの状態文が常に出る | 正常時には要らない情報。異常時だけ出せばよい |
| 「全候補を見る」「検索を中止」 | 一般的な検索画面に無い操作で、意味を考えさせる |
| tools/game で検索するとカードが消え、共通の行一覧に置き換わる | 結果がページのデザインから浮く。9件・8件のカタログで別の一覧に切り替える理由がない |
| 長いプライバシーの説明文が常に出る | 一覧より目立つ。告知は1行と詳細のダイアログで足りる |
| 日刊のポータルに検索欄が2つある（ヘッダーと「記事を横断検索」） | どちらに打てばよいか迷う |

目標は「何も考えずに使える」こと。打てば下に候補が出て、候補を選べばそのページへ、Enter を押せば結果の一覧が出る。

## 2. 範囲

対象は 404・tools・game・日刊2誌（ポータルと号のページ）の検索 UI。4画面で**操作と構造は共通**、**見た目は各ページ**に従う。

変えないもの:

- `japanese-search.js` の照合・正規化・読み、`search-data.js` の取得・検査・版、`site-search.js` の②の通信
- Worker（magi2）の `/search/api/rank`・`/search/api/click` の契約。クリックの `list` は既存の `suggest`・`local`・`semantic` のまま使う（`workers/magi2/src/index.js` の `CLICK_LISTS`）
- ②を送るのは明示の検索だけ、入力中はどこにも送らない、検索語を URL に載せない、`st-analytics=off` を守る、tools の CSP を広げない
- 404 の③（Shinya Takeda AI に聞く）の送信の中身と、③を出す条件（`aiAllowed`）の考え方

入れないもの: 人気の検索語の表示（9章）、検索履歴、検索語の URL 化。

## 3. 共通の操作

### 3.1 検索欄

```
┌──────────────────────────────────┬────┐
│ ツールを検索（例: PDF、QR、CSV）      × │ 🔍 │
└──────────────────────────────────┴────┘
```

- `<form role="search">` の中に `type="search"`・`enterkeyhint="search"` の input と、虫眼鏡のアイコンの送信ボタン（`aria-label`「検索」）を置く。見出しは目に見えない `label` にする（読み上げは残す）。
- 欄の中に薄く対象を書く（placeholder。文言は 3.9）。
- 入力があるときだけ、欄の右端に消去ボタン（×、`aria-label`「検索をやめる」）を出す。押すと入力を消し、結果も閉じる（3.4）。ブラウザ標準の消去ボタンは CSS で消し、ブラウザによる違いを無くす。
- タップの的は 44px 以上にする（日刊のヘッダーの小さい画面は 4.4）。

### 3.2 候補の枠（ドロップダウン）

```
┌──────────────────────────────────┐
│ 🔍 「pdf」で検索                    │ ← 常に先頭。選んで Enter／押す ＝ 検索の確定
│ ▸ **PDF** Studio            editor │ ← 最大6件。押すとそのページへ移る
│ ▸ …                                │
├──────────────────────────────────┤
│ Enter で検索。AIで関連する候補も探します ⓘ │ ← listbox の外。ⓘ で詳しい説明
└──────────────────────────────────┘
```

- 欄の部品（欄の `<form>` と候補の枠）の中にフォーカスがあり、入力が空でないときに、欄の直下に**重ねて**出す（下の内容を押し下げない）。
  - 閉じるのは、フォーカスが欄の部品の外へ出たとき（`focusout` の `relatedTarget` が部品の外）、外を押したとき、Esc、候補の選択、検索の確定。
  - 欄から Tab で消去ボタン・虫眼鏡・枠の末尾のⓘへ移っても閉じない。枠の中へのフォーカスの移動は、閉じる条件に含めない。
  - 候補の行は `aria-activedescendant` で選ぶので、フォーカスを受けない。行の `<a>` には `tabindex="-1"` を付け、枠の中で Tab が止まるのはⓘだけにする。
  - 枠の中の `pointerdown`（候補の行・先頭行）は `preventDefault` して、フォーカスを欄に残す。押した瞬間に欄からフォーカスが外れると、`relatedTarget` が `null` になる環境（リンクを押してもフォーカスを移さない macOS の Safari など）で枠が先に閉じ、続く `click` が行に届かないため。ⓘの `pointerdown` は止めず、ⓘにフォーカスを移す。
  - ⓘでダイアログを開いている間は枠を閉じてよい。ダイアログを閉じたら、フォーカスを欄に戻す（3.7）。
- 中身は、下書き（3.4）での①の照合結果の先頭6件（Phase 4 と同じ照合と並び）。各行は題名と、右に小さく種類（ツールのカテゴリー・ゲームのジャンル・記事の日付など）を出す。説明文は出さない。
- 枠には一致の件数を出さない。PRD 3.1 の「サジェストと該当件数」を置き換える。件数は確定後の結果の見出し（3.4）で出す。
- 題名のうち、入力と一致した部分を太字にする。一致は、ASCII の英字の大文字・小文字だけを区別せず、それ以外は字のままで比べる（全角・かな・読み・ローマ字での一致は太字にしない）。太字は `textContent` で分けて組み、`innerHTML` を使わない。
- 先頭行「「〇〇」で検索」は、0件でも出す。末尾の告知の行は 3.7 の告知を兼ねるので、枠を出すときは常に出す。
- 基礎データの読み込み中、または読みの準備中で一致が0件のときは、先頭行の下に「読み込み中…」と出し、「見つかりません」とは言わない（PRD 5章の約束）。準備ができたら、入力とフォーカスを動かさずに中身を入れ替える。基礎データの取得に失敗したときは、先頭行の下に失敗の文（3.9）を出す。
- 小さい画面では画面の幅いっぱいに出す。欄にフォーカスしたとき、欄が画面の上のほうに来るようスクロールして、キーボードの上に枠が入る余地を作る（日刊のヘッダーは sticky なのでスクロールしない）。

### 3.3 キーボードと IME

- ARIA の combobox（1.2）に従う。input に `role="combobox"`・`aria-expanded`・`aria-controls`・`aria-activedescendant`。先頭行と候補6件が listbox の option。
- ↑↓ で option を移る（端で折り返す）。何も選んでいない Enter と、先頭行を選んだ Enter は検索の確定。候補を選んだ Enter はそのページへ移る。
- Esc は、枠が開いていれば `preventDefault` して枠を閉じるだけにする（Chrome の `type="search"` は Esc で値を消すため、標準の動作を止める）。枠が閉じていれば入力を消す。このとき結果は閉じない（3.4）。
- IME 変換中の Enter・上下キー・Esc を奪わない、変換確定の Enter を検索にしない、の守り（Phase 4 の `composing`・`imeEnterHeld`）はそのまま残す。

### 3.4 検索の確定と結果

確定の操作は、Enter・虫眼鏡・先頭行の3つ。Phase 4 の「全候補を見る」は先頭行に吸収する。

**下書きと確定の分離**: 共通部品に「確定した検索語」を新しく持たせる。入力欄の値を「下書き」と呼ぶ。

- 結果を出したあとに欄を書き換えても、次に確定するまで結果はそのまま残る（Google と同じ）。②もこのときは捨てない。
- 結果を閉じて検索前の画面（tools/game のカタログ、日刊のアーカイブ、404 の「もしかして」）に戻すのは、消去ボタン（×）と、空のまま確定したときだけ。Esc やキー操作で欄が空になっても、結果は閉じない。

どちらの語を使うかは、次の表に従う。ページ側の受け手（`onConditions`・`onState`）も確定した語を受け取る。

| 使い道 | 語 |
| --- | --- |
| 候補の枠の照合、`promote`（候補の枠の並び） | 下書き |
| クリックの記録で `list` が `suggest` のもの | 下書き |
| 結果の一覧の照合と見出し、`promote`（結果の並び） | 確定した語 |
| ②の送信、②の版・世代の照合 | 確定した語 |
| クリックの記録で `list` が `local`・`semantic` のもの | 確定した語 |
| `onConditions`・`onState` の `query`、計測（`track`） | 確定した語 |
| 404 の③の対象（`ai.query`）、日刊への移動のリンク | 確定した語 |

結果の一覧の構造（絞り込みと並べ替えの帯は 3.6）:

```
［絞り込み・並べ替えの帯］                          ← 検索の前から出す（3.6）
「pdf」の検索結果 5件
┌ AIが見つけた関連候補 ──────────────┐         ← ②（3.5）。1行ずつの短い表示
│ …                                      │
└─────────────────────────┘
［①の結果。ページの普段のカード・行で描く］
          もっと見る（残り 12件）
```

- 見出しに確定した検索語と①の件数を出す。確定のたびに、読み上げ用の status で件数を1回だけ知らせる。
- **基礎データの準備前に確定したとき**（`mount` の後、基礎データの取得中。号のページで `mount` の前に確定したときは 4.4）: 確定を取りこぼさない。保留として、確定した語・条件と、**②を送ってよいか**の3つを保ち、結果の場所に「読み込み中…」を出す。
  - ②を送ってよいのは、明示の確定（Enter・虫眼鏡・先頭行）と、3.8 の有効な目印を持つ受け渡しだけ。通常の受け渡し（`setQuery` で受けた `#q=`・タグ・ウォッチ・404 からの移動）は、保留しても②を送ってよいとはしない。
  - 準備ができたら①を出す。②を送ってよい保留なら②を1回送る。そうでなければ、3.8 と同じく②の代わりに「AIで関連する候補も探す」のボタンを出す。
  - 準備までに条件（絞り込み）が変わっていたら、②を送ってよい保留でも送らず、3.6 と同じくボタンを出す。準備までに別の語で確定し直したら、新しい確定（とその②の可否）だけを扱う。
  - 基礎データの取得に失敗したら、結果の場所に失敗の文（3.9）を出し、②は送らない。
- **読みの準備中・失敗のときの結果**（PRD 5章）: 読みが準備中でも、文字の一致で①を出す。
  - 見出しの件数の後ろに「（読み込み中）」を添え、0件でも「見つかりませんでした」とは言わず「読み込み中…」と出す。
  - 読みの準備ができたら、確定した語で①を数え直して並べ直し、見出しの件数を更新し、status で新しい件数を1回だけ知らせる（3.9「読みを含めた件数」）。入力とフォーカスは動かさない。
  - 読みの準備に失敗したら、見出しに「（文字の一致のみ）」を添え、0件なら「「〇〇」に文字で一致するものは見つかりませんでした」と出す。読みまで調べた「該当なし」とは言わない。
- ①は最初に20件出し、「もっと見る」で20件ずつ足す。Phase 4 の100件ずつの決まりを置き換える。最後の1件まで開ける点と、既存の行を作り直さない点は変えない。
- 確定したとき、結果の見出しが画面の外にあればそこへスクロールする（日刊のポータル）。画面の中にあればスクロールしない（404・tools・game は欄のすぐ下に結果が出る）。
- 指で操作する端末（`pointer: coarse`）では、確定したら欄のフォーカスを外し、キーボードを閉じて結果を見せる。マウスの端末ではフォーカスを欄に残す。

### 3.5 ①と②の並べ方

①は確定した瞬間に出す。②が返っても、①の並びも位置も動かさない。読んでいる一覧が跳ねないようにするため。

- ②は、確定のたびに Phase 4 と同じ条件で1回だけ送る。同じ条件の②が既に返っている（または送っている途中の）ときに確定し直しても送り直さない。②を送らずボタンを出している状態（受け渡し・絞り込みの変更の後）での確定は明示の操作なので、②を送る。
- 送ったら、結果の見出しの下に「AIで関連する候補を探しています…」と、**3行分の高さの仮の枠（スケルトン）**を出す。②の候補はこの高さに収まる1行ずつの短い表示（題名と種類）で描き、tools/game でもカードにしない。これで、②が返っても下の①が押し下げられない。
- ②が返ったら、②の候補から、**確定した時点で①の最初の20件に入っている候補**（読みの準備ができて①を並べ直したときは、並べ直した後の最初の20件）を除き、②の順（Jev の確率順）で最大3件を枠に出す。4件以上あれば「すべて表示」で残りを開く（開いた分だけ下が動くのは、本人の操作によるので許す）。
  - ①の21件目より後ろにある候補は除かない。①で埋もれている正解を②が上へ拾い上げるのが、Phase 4 の評価（正解の上位5件到達）で確かめた②の役目だから。「もっと見る」で開いた①と重なって見えることは許す（Google と同じ扱い）。
- 除いたあとに0件なら、仮の枠を畳む。上へ詰まる動きになり、読んでいる位置より下が上がるだけなので、押し下げより気になりにくい。
- ①が0件で②に候補があるときは、②の候補を本体の一覧として「「〇〇」に一致するものはありませんが、近いものがあります」の見出しで出す。このときは②の候補をページの普段のカード・行で描く。どちらも0件なら「「〇〇」に一致するものは見つかりませんでした」と出す。
  - 「①が0件」と決めるのは、読みの準備が終わるか失敗した後だけ。読みの準備中は、②の候補を仮の枠に短い表示で出しておき、読みが終わってからこの判断をする。
  - ①が0件で②の応答を待っている間は、見出しを「「〇〇」の検索結果」（件数なし）にし、仮の枠の「AIで関連する候補を探しています…」だけを出す。「見つかりませんでした」は、②が0件で返るか、②を送らない・送れない（停止中・上限・失敗・受け渡しでボタンを出した）と決まってから出す。
- 読み上げ: ②の候補を枠に出したら、status で「AIが関連する候補を{n}件見つけました」を1回だけ知らせる（除いたあとに0件なら知らせない）。①の件数の知らせ（3.4）とは別の文にし、同じ文を繰り返さない。
- ②が停止中・上限・失敗・版の更新中のときは、仮の枠を畳み、画面に文を出さない（①はそのまま使える）。読み上げ用の status にだけ短く入れる。版ずれからの自動復帰は Phase 4 のまま。
- Phase 4 の判定件数の表示（coverage）と「検索を中止」は画面から外す。新しい確定、または消去で、②は自動で捨てる。

### 3.6 絞り込みと並べ替え

**絞り込みと並べ替えは、検索欄と中身（カタログ・アーカイブ・結果）の間の「帯」に置き、検索の前から出す。** いまも tools/game のカテゴリー・ジャンル・並べ替えはカタログに、日刊の月はアーカイブの一覧に、検索しなくても効いている。結果の中にしか置かないと、これらが検索しないと触れなくなる。

- 絞り込みの種類は Phase 4 と同じ（tools はカテゴリー、game はジャンル、日刊はカテゴリー・地域・月、404 は無し）。
- 検索の前に出す絞り込みは、adapter の `filtersBeforeSearch` で決める（5.1）。tools はカテゴリー、game はジャンル、日刊は月だけ（日刊のカテゴリーと地域は、検索していないときに効く先が無いので、確定したときに帯へ足す）。
- 結果を出したあとに絞り込みを変えたら、①はその場で数え直す。②は送り直さず、②の枠を「AIで関連する候補も探す」のボタン1つに置き換える。押せば、その条件で②を1回送る（明示の操作）。
- 並べ替えは①だけに効く。②の枠は並べ替えで消さない。選択肢が1つ以下のとき（日刊、404）は出さない。
- tools/game の並べ替え:
  - 検索の前は「新しい順・古い順・タイトル順」（既定は新しい順）。
  - 確定したら先頭に「関連順」を足して選ぶ。結果を出している間に選び直したら、その順を保つ。
  - 結果を閉じたら「関連順」を外し、検索の前に選んでいた順に戻す。

### 3.7 送信の告知

送る相手と中身は Phase 4 と同じ。告知の出し方だけ変える。

- 欄から確定する人は、打っている間に候補の枠の末尾の1行（3.2）を目にする。これを送信前の告知とする。枠を Esc で閉じてから虫眼鏡を押す経路もあるが、そこまでに一度は枠が出ている。
- この1行が送信前の唯一の告知になるので、「AI」とだけ書かず、送り先（TypeSafe AI）と送るもの（検索語）を1行の中に書く（3.9）。端末の中で動く AI と区別がつかないと、「中身を送る処理を持たない＋通信先を制限」を掲げる tools の一覧の説明と食い違うため。
- 枠を通らずに②を送る操作は「AIで関連する候補も探す」ボタンだけで、ボタンの隣に同じⓘを置く。
- 詳しい説明は、ⓘで開く `<dialog>` に移す。日刊のポータルの `archiveSearchInfo` と同じ形にする。中身は、共通の段落と、画面ごとに足す段落に分ける。
  - 共通の段落（4画面）: TypeSafe AI の学習・保持・処理場所、IP の記録、クリックの記録と90日、3人以上の集計の公開、ポリシーへのリンク。共通の辞書から出す。
  - アクセス解析の段落（404・日刊だけ）: 検索語を Google アナリティクスに記録すること（メールアドレスや電話番号は伏せる）、アクセス解析を止めれば送らないこと。いまの 404 の `analytics-info-text` と日刊の `archiveSearchInfo` の2段落目の内容。adapter の `analyticsNotice: true` で足す（5.1）。tools と game は検索語をアクセス解析に送っていない（adapter に `track` が無い）ので出さない。
  - adapter に `track` で検索語（`search_term`）を送る処理を足すときは、同時に `analyticsNotice` も付ける。
- ダイアログを閉じたときのフォーカス: 候補の枠のⓘから開いたときは、枠がもう閉じているので欄に戻す（入力が残っていれば枠がまた開く）。それ以外のⓘ（②のボタンの隣、日刊の節の見出し）から開いたときは、開いたⓘに戻す（`<dialog>` の標準の動作）。
- tools 一覧の FAQ・JSON-LD の「この一覧の検索ボタン／Enterは…」は、送る条件が変わらないのでそのまま使える。

### 3.8 受け渡し

`#q=`（tools/game/日刊）、日刊のタグ・ウォッチの★、404 から日刊への移動で受け取った語は、欄に入れて①だけで確定する。②は送らず、②の枠の場所に「AIで関連する候補も探す」のボタンを出す（PRD 3.2 を守る）。基礎データの準備前に受け取ったときも、準備の後に②を送らない（3.4 の保留は「②を送ってよい」を持たない）。

**例外: 日刊の号のページのヘッダーで確定したとき**。号のページで Enter を押すとポータルの `#q=` へ移るので、そのままでは②が送られない。枠の告知（3.2）と食い違うため、次の手順でポータルでも明示の操作とみなす。

1. 号のページのヘッダーで確定したら、移る直前に sessionStorage の `st-search-explicit` へ `{scope, query, at}` を書く。`query` は照合と同じ正規化をした確定の語、`at` は時刻。
2. ポータルは `#q=` の語を受け取ったら、まず `st-search-explicit` を読んで**すぐ消す**（一度きり）。
3. `scope` が一致し、`query` が `#q=` の語の正規化と一致し、`at` から30秒以内なら、明示の確定として②を送る。ポータルの基礎データがまだ準備中なら、「②を送ってよい」を持つ保留にする（3.4）。
4. そうでなければ通常の受け渡しとし、②のボタンを出す。外部のリンクから来た `#q=` はこの目印を持たないので、②は送られない。

sessionStorage は同じタブの同じサイトにだけ残り、どこへも送らない。読み書きできないブラウザでは通常の受け渡しになる。

## 4. 画面ごとの見た目

共通部品はフックとなる class（`st-search-*`）を付けた DOM を作り、色・字体・角丸・影はページの CSS とトークンが決める。結果の行は、ページが渡す描画関数（5.1）がページの部品で描く。

### 4.1 404

- 欄: いまの `--surface`・`--border`・`--accent`（緑）・角丸10px で、大きめに1本。マウスで来た人には、いまどおり自動でフォーカスする。
- 入力が空のうちは、欄の下に「もしかして」（`#path-suggestions`）を出す（いまのまま）。確定したら隠し、結果を閉じたら戻す。
- 結果の行は、いま「もしかして」と③の結果で使っている `.result-list` の行（`resultItem`）に揃える。種類（ツール・ゲーム・記事・ページ）を小さく添える。
- 結果の末尾に、日刊への移動（いまの `#daily-search`）と、③の入口（`#ai-search`）を置く。③の目立たせ方（②の結果がそろったときだけ `is-quiet`）はいまの扱いを保つ。
- ③は確定した語を対象にする（3.4）。いまの `currentQuery()`（入力欄を直接読む）での照合は、確定した語との照合に置き換える。③を始めたときに②を止める `handoff()` は残す。
- 「サイトの全体」（`#sitemap` のタイルとパネル）は検索部品の外、検索の下に置く。

### 4.2 tools

- 欄と枠: ページの等幅のラベル（`--font-mono`）と、カテゴリーの色（`--cat-*`）。候補の行には、カテゴリー色の点とカテゴリー名を添える。ツールの画像（`imageUrl`）は OGP 用の大きな画像なので、枠では読まない。
- 帯: カテゴリーはカテゴリー色のチップを横に並べる（`aria-pressed` のボタン）。並べ替えはページのセレクト。
- 結果: **いつものツールのカード**（`createCard`）を、カタログと同じグリッドで並べる。②の候補は 3.5 の短い表示（①0件のときだけカード）。
- 確定していないときは、いまどおりカタログを出す。カタログの出し分けは `onConditions` の `query`（確定した語）で行い、打っている間はカタログを隠さない。カタログの JSON-LD（`updateItemListSchema`）は検索で書き換えない。

### 4.3 game

- 欄: NES.css の `nes-input`、虫眼鏡は `nes-btn`。字体は Press Start 2P。
- 枠: `nes-container is-rounded`。選んでいる行の頭にゲームのメニューのような ▶ を出す。候補の移動と確定で、ページの既存の `soundPop` を鳴らす。
- 帯: ジャンルの `nes-btn` を並べる。
- 結果: **いつものゲームのカード**（`createCard`）。②の候補は 3.5 の短い表示で、カードに「AI」の印は付けない（カードの「[AI]」は制作に使った AI の表示で、意味がぶつかるため）。

### 4.4 日刊2誌

**検索欄はヘッダーの1本にまとめる**（2026-10-12 決定）。ポータルの「記事を横断検索」の節から入力欄を外し、帯と結果の置き場にする。

- 欄: いまのヘッダーの `.header-search`（`daily-base.css`）に、共通部品を後から取り付ける（5.1 の `input`）。`.header-search` は `overflow: hidden` なので、候補の枠はフォームの外、ヘッダーの直下に置く。ヘッダーは sticky なので、枠もヘッダーに付いて動く。
- ヘッダーの確定を受けるのは、常に `daily-ui.js` と共通部品のどちらか一方。`mount` が終わったら共通部品が受け、`daily-ui.js` のヘッダーの処理（`initSearchHandoff` の `submit`）は手を引く。
  - ポータルはページを開いたときに `mount` する（いまと同じ）。いまのポータルではヘッダーの確定を `daily-ui.js` が `searchFor` → `setQuery`（受け渡し、②なし）へ流しているが、`mount` の後は共通部品の明示の確定になり、②も送る。
  - ポータルでも、ヘッダーの欄は `mount` の前から HTML にあるので、スクリプトの読み込みが終わる前に打って確定できる。この間は候補の枠（末尾の告知）がまだ出ていないので、号のページと同じく、`daily-ui.js` が受けて**②を送ってよいとしない保留**（通常の受け渡しと同じ）として共通部品へ渡す。準備ができたら①を出し、②の代わりにボタンを出す。告知を見る前に送らないため。IME の守りは号のページと同じ。
  - 号のページの `mount` の前後は下の「号のページ」のとおり。
- **小さい画面（720px 以下）**: いまの欄は幅 `clamp(92px, 25vw, 150px)`・高さ36px で、そのままでは打ちにくく、44px の的も満たせない。フォーカスしたら欄をヘッダーの幅いっぱい・高さ44px に広げ（ブランドの表示とボタンをその間だけ隠す）、候補の枠は画面の幅でヘッダーの直下に出す。
  - フォーカスが欄の部品の外へ出たら、入力が残っていても元の幅に戻し、ブランドとボタンを出す。確定したとき（3.4 で指の端末はフォーカスを外す）もこれで戻るので、結果を見ている間もヘッダーのボタンが使える。
  - 戻した欄には確定した語がそのまま入っている（幅に収まらない分は欄の中で切れる）。消去ボタンは広げている間だけ出す。結果を閉じたいときは、欄に触れて広げてから×を押す。
- 候補の行: 日付（`2026-10-11`）と記事名。媒体ごとの CSS（`nitori-daily.css`・`retail-tech-daily.css`）の色に従う。
- ポータルの「記事を横断検索」の節:
  - 検索の前は、帯（月の絞り込み。月はいまどおりアーカイブの一覧に効く）と、「ページ上部の検索欄で記事を探せます」の案内だけを出す。案内はボタンで、押すとヘッダーの欄にフォーカスする。
  - 確定したら、帯にカテゴリーと地域を足し、その下に結果を出す。結果の見出しが画面の外ならそこへスクロールする（3.4）。
  - 結果の行は、アーカイブの行（日付の列と記事名）と同じ見た目にする。
- ⓘ: 節の見出しの隣のⓘ（`archiveSearchInfoOpen`）は残し、枠の末尾のⓘからも同じダイアログを開く。
- **号のページ**でも候補を出す。
  - 検索の JS と索引は、ページを開いたときではなく、欄に初めてフォーカスするか入力したときに読む。読み込みは `daily-ui.js` が受け持ち、共通の6ファイル（`search-analytics.js`・`japanese-search.js`・`site-search.js`・`search-ui.js`・`search-data.js`・`search-ui.css`。2026-10-12 時点で gzip 合計約30KiB）を読んでから `mount` する（5.1）。読む資産と版は `daily_engine.py` の `SEARCH_ASSETS` が正本で、ポータルのタグと、号のヘッダーの `data-search-assets`（遅延読み込みの一覧）の両方をそこから作る。並べて取得し、JS は書いた順に実行する（`async=false`）。`data-search-assets` の無い古い号では遅延読み込みをせず、従来の確定だけを使う。
  - 候補を選べば、その記事へ直接移る。
  - `mount` が終わった後に確定したら、3.8 の目印を書いてポータルの `#q=` へ移る。ポータルでは②も送られる。`mount` の後は候補の枠（末尾の告知を含む）が出ているので、告知を見る前に送ることにはならない。基礎データの取得中なら、枠には「読み込み中…」と告知が出ている。
  - **`mount` が終わる前**（6ファイルの取得中、または取得に失敗した後）は、`daily-ui.js` の既存のヘッダーの処理が確定を受ける。
    - この間の確定は、目印を書かずにポータルの `#q=` へ移る（空なら今どおり `#archiveSearch`）。告知の枠がまだ出ていないので、ポータルでは通常の受け渡しになり、②の代わりに「AIで関連する候補も探す」のボタンが出る（3.8）。検索は取りこぼさず、②は告知の付いたボタンから送る。
    - この間も IME の守りを `daily-ui.js` が持つ。`compositionstart`〜`compositionend` の間と、`isComposing`・`keyCode 229` の Enter では移らない。変換確定の Enter に続く `keyup` までは、同じキーで確定しない（Phase 4 の `imeEnterHeld` と同じ考え方）。
    - 取得に失敗したら再取得はせず、ヘッダーはいまの号のページと同じ動き（候補なし、Enter でポータルへ）を続ける。
  - 取得中に打った文字は、`mount` が終わってから照合して候補を出す。そのときフォーカスが欄にあれば枠を開く。
- 読む索引の量（2026-10-12 実測、`_site`）:

  | 媒体 | 号数 | `search-index.json` | `search-readings-2026.json` | gzip 合計 |
  | --- | --- | --- | --- | --- |
  | nitoridaily | 30 | 196,635 B（gzip 54,304） | 314,948 B（gzip 62,016） | 約113KiB |
  | retailtechdaily | 31 | 217,641 B（gzip 59,606） | 326,286 B（gzip 65,576） | 約122KiB |

  1号あたり gzip 約3.8〜3.9KiB で増える。gzip 合計が 1MiB に届くのは、retailtechdaily が約260号（2027年5月末）、nitoridaily が約270号（2027年6月上旬）。その前に、号のページでは最新の年だけを先に読む形を検討する。ポータルは全年度を読む（いまと同じ）。
- 日刊のポータルと号のページは `daily_engine.py` が書くので、ヘッダーと節の HTML はそちらを直し、全号を作り直す（再生成だけの号は `Date-Sync: skip`）。

## 5. 作り

### 5.1 共通部品の分け方

`search-ui.js` の `mount` の中を、**制御**と**表示**に分ける。ファイルは1つのまま。

- 制御（いまの `mount` の大半をそのまま移す）: 状態、IME、①の照合、②の送受信と世代、版ずれからの復帰、クリックの記録、計測（`track`）。新しく持つのは、確定した検索語と語の使い分け（3.4）、基礎データの準備前の確定の保留（語・条件・②を送ってよいか）と、読みの準備後の数え直し（3.4）、20件ずつの表示上限。3.8 の目印の読み書きは日刊の `daily-ui.js` が持ち、共通部品は `setQuery(value, {explicit: true})` で明示操作かどうかだけを受け取る。
- 表示: 欄・消去・虫眼鏡・候補の枠・帯・結果の見出し・②の枠・「もっと見る」・status・ⓘのダイアログを、共通の DOM で作る。

`mount(container, adapter)` の adapter に足す項目。**すべて省略でき、省略したときは共通の既定で動く**（欄も共通部品が作る）。Pages は `?v=` に関係なく最新のファイルを返すので、ブラウザに残った古い HTML が新しい `search-ui.js` を読んでも検索が使えるようにするため（見た目は崩れてよい）。

| 項目 | 内容 |
| --- | --- |
| `input` | 既存の `<form role="search">`。渡されたらその中の input とボタンを使い、欄を作らない（日刊のヘッダー）。借りた `<form>` は DOM の中で動かさず、候補の枠を直後に置く（動かすとフォーカスと IME の変換が途切れ、読み込み中に打ち始めた入力が途中で確定される）。「欄の部品の中」は `<form>` と枠の両方で判定する |
| `results` | 帯と結果を出す要素。無ければ `container` の中に作る（日刊は「記事を横断検索」の節） |
| `placeholder` | 対象名入りの文言（日英） |
| `classes` | 部品ごとに足すページの class（例: game の `{input:'nes-input', button:'nes-btn', panel:'nes-container is-rounded'}`、tools/game の結果の一覧にカタログのグリッドの class） |
| `filterChips` | true なら、絞り込みを `aria-pressed` のチップで描く。省略時はセレクト。チップの class は `classes.chip` |
| `filtersBeforeSearch` | 検索の前から帯に出す絞り込みの key（3.6）。省略時はすべて |
| `renderItem(record, ctx)` | 結果の1件を描いて要素を返す。`ctx` は `{href, locale}`（`href` は検査済みの行き先）。①と、①0件のときの②の本体の一覧で呼ぶ。候補の枠と②の短い表示は呼ばずに共通の行で描く。省略時は共通の既定（題名と説明） |
| `renderSuggestion(record, ctx)` | 候補の行の右の種類の表示を返す。省略時は種類を出さない |
| `onResults({query, open})` | 結果の開閉をページへ知らせる（tools/game のカタログ、404 の「もしかして」・③、日刊の案内） |
| `analyticsNotice` | true なら、ⓘの説明にアクセス解析の段落を足す（3.7）。404・日刊で付ける |

号のページの遅延読み込みは `daily-ui.js` が受け持ち、欄に触れてから6ファイルを読んで `mount` する。`mount` の時点で利用者は欄に触れているので、adapter に遅延の項目は持たせない（`mount` はすぐに `loadBase` を呼ぶ）。

`renderItem` の契約:

- 返す要素の中で、そのページへ移る主なリンクに `data-st-primary` を付ける（要素そのものが `<a>` ならそれでもよい）。game のカードのように、外枠が `<article>` で中にボタンとリンクを持つ形を許すため、共通部品は外枠を `<a>` にしない。
- 共通部品は、その記録の行き先を `safeHref` で検査し、ルートからの相対 URL（例 `/tools/pdf-studio/`）を `ctx.href` として渡す。ページは主なリンクの `href` に **`ctx.href` をそのまま入れる**。自分の持つ URL（絶対 URL など）を使わない。
  - tools の `normalizeRecords` は URL を絶対 URL（`url.href`、例 `https://tk.st/tools/pdf-studio/`）に直して `record.url` に入れる。そのままカードを流用すると次の検査で一致せず、全件が描かれない。そこで、描く直前にページの記録を写して `url` を差し替える（`createCard({...pageRecord, url: ctx.href, external: false})`）。game の `createCard` も同じく `url` を `ctx.href` に差し替えて呼ぶ。カタログの描画は今のまま。
- 共通部品は、主なリンクの `getAttribute('href')` が `ctx.href` と文字列で一致することを確かめる。一致しなければその1件を描かない（ページの描画の誤りで、検査していない URL を出さないため）。一致すれば記録用の class（`st-search-link`）を足し、一覧の要素に `data-st-search-list`（`suggest`・`local`・`semantic`）を付ける。クリックの記録は、この2つの目印で開いたページと一覧を見分ける。
- 中身の組み方: 新しく書く描画は `textContent` と要素で組む。tools/game の既存の `createCard` は、値がサイトの正本 JSON（`tools.json`・`game.json`）で、`escapeHTML` を通してから `innerHTML` に入れているので、そのまま使ってよい。日刊・404 の描画では `innerHTML` を使わない。

ページ側の受け手で変わるもの:

- `onConditions`・`onState` の `query` は確定した語になる（3.4）。tools/game の `catalogueQuery`、404 の `searched()`・`syncAI()`・日刊へのリンク、日刊の `onConditions` はこれに合わせる。
- `setQuery`・`handoff`・`setLocale`・`ready`・`state`・`run`・`cancel` は名前と役目を保つ。`setQuery` は 3.8 の受け渡し（①だけで確定）になる。`{explicit: true}` を渡したときだけ明示操作として②を送る（日刊が目印を確かめた場合）。

## 7. 公開と戻し方

- 公開は Phase 4 と同じく `main` への push。Worker は変えないので、デプロイは無い。
- **前提**: 共通部品（`assets/`・`job/assets/`）の版と、日刊の全号・ポータルの HTML は、常に同じ push で揃えて出す。片方だけが公開されると、号のページの欄が動かない、または古い欄に新しい部品が付く。`build.sh` は日刊の HTML を作り直さない（リポジトリにある HTML をそのまま写す）ので、push した HTML がそのまま公開される。
- 1〜5 は作業用のブランチで進める。日刊の生成物はブランチでコミットしない。日刊の bot は毎日 `main` へ新しい号とポータルを書くので、ブランチで作り直したポータルや号はマージのたびに衝突し、ブランチを切ってから出た号は古い形のまま残る。ブランチでは `daily_engine.py` と `job/assets/` だけを直し、検証は手元で作り直した出力（コミットしない）で行う。

公開の手順（すべて手元で済ませてから、push は最後の1回だけ）:

1. bot の時刻（retailtechdaily 01:55、nitoridaily 02:05 JST）の前後を避ける。`git fetch` して、手元の `main` を `origin/main` に揃える。
2. 手元の `main` に作業用のブランチを `git merge --no-ff` でマージする（まだ push しない）。早送りにすると、戻すときに1つのコミットとして戻せないため。
3. 両誌の生成スクリプトの `--rebuild`（`generate-nitori-daily.py --rebuild`・`generate-retail-tech-daily.py --rebuild`）で、全号とポータルを作り直す。`Date-Sync: skip` を付けて1つのコミットにする（まだ push しない）。
4. `bash build.sh` で出荷物を作り、8章の検証を `_site` で通す。
5. もう一度 `git fetch` する。`origin/main` が進んでいたら（bot の新しい号など）、それを取り込んでから 3〜4 をやり直す。新しい号は古い生成器で作られているため。
6. マージと作り直しの2つのコミットを、**1回の push** で出す（`.github/scripts/push-with-retry.sh` は使わない。弾かれたら取り込んで 3〜5 からやり直す）。

戻し方（これも1回の push で出す）:

- 作り直しのコミットとマージの両方を、新しい順に `git revert` する（作り直しを先に戻し、次にマージを `-m 1` で戻す）。マージだけを戻すと、作り直した新しい HTML が残り、古い共通部品と組み合わさって公開される。
- 日刊の全号を戻す revert のコミットにも `Date-Sync: skip` を付ける（`git revert --no-commit` の後にメッセージへ書いてコミットする）。付けないと、`sitemap.yml` の `update-modified.py` が戻しただけの号の `dateModified` を一斉に進める。
- 公開の後に bot が新しい号を足していたら、その号は新しい生成器で作られている。2つを戻した後、戻した生成器で `--rebuild` をもう一度走らせ、`Date-Sync: skip` を付けてコミットする。
- `bash build.sh` と8章の検証（`test-phase4-legacy-ui.mjs` を含む）を通してから、上の revert と作り直しのコミットをまとめて1回で push する。公開の手順の 1・5・6 と同じく、bot の時刻を避け、`origin/main` が進んでいたら取り込んでやり直す。
- ②を止めるときの手順（`SITE_RANK_ENABLED` → 404 の `RANK_ENABLED`）は変わらない。止めている間は、②の仮の枠と「AIで関連する候補も探す」を出さず、枠の末尾は「Enter で検索」だけにする（3.9）。
