# サイト内検索 Phase 4 検証計画書

実装中（2026-10-12更新）。生成・照合・新共通UI・旧HTML互換をローカルで部分検証済み。詳細と未実施範囲は[実装記録](../.github/site-search/phase4/implementation-progress.md)。対象は[PRD](site-search-phase4-prd.md)、契約は[設計書](site-search-phase4-design.md)、順序は[実装計画書](site-search-phase4-plan.md)。Phase 3の合格記録をPhase 4の合格として数えない。

2026-10-12の追加検証は一般60語、tools/gameの固定80問の実Jev、10k共通UIの入力p95、7,500件の実日刊adapter、Blob Workerの生バイトhash・内容保持・移譲後の縮退・取消、5画面の小画面・CSS拡大・焦点・重複通知・並べ替え時の②破棄、674ファイルの出荷ビルド、Windowsの10k生成ピークRAM234.7/285.5MiBとブラウザメモリ。準備は約2.7〜3.2秒へ短縮。初回20入力・最大約0.225秒の準備中停止は制約として記録する。ChromiumのIME入力経路は確認したが、OSの実機IMEではない。Linux／Pages、実機IME／読み上げ、実計測を含む本番URL回帰と公開確認は未実施。

fixtureには基礎索引のhash、辞書・解析器・補正・revision、作成日、正解を付けた担当を残す。未知語の読みが空の場合に架空の正解を付けない。tuneを見て修正したら、未見finalの正解を結果に合わせて変更しない。

版ずれのfixtureは404・tools/game・日刊の各基礎データで旧版→新版を作る。日刊はheadだけでなく過年度のPromiseキャッシュも古い状態から始める。入力や検索の確定操作を行わず、版ずれの検知だけで復帰が始まることを確認する。基礎データだけ成功・読みだけ失敗、基礎データも失敗、再取得後も不一致、取得中の条件変更と同時の不一致検知を分け、読みだけの再取得では合格にしない。自動復帰の前後で通信数を数え、画面ごとの復帰処理が1回で打ち切られ、成功・失敗のどちらでも後続の入力・filters・locale・検索実行・追加表示から繰り返されないことを確認する。復帰中の入力変更は最新条件へ反映し、入力値・フォーカスを保つ。ページの再読み込みは新しい初期取得として扱う。版ずれを検査できない取得失敗と契約違反も分けて文字検索への縮退を確認する。manifestには外部URL・遡り・別媒体・重複年度を加え、取得先の制約を検証する。

②のgeneration不一致も同じ復帰1回枠を使う。siteのrank_generationと読み用hashを別にし、一覧JSONとWorkerの公開候補の混在、①と②が同時に版ずれを検知するケースを加える。②の古い行を表示・重複除去へ採用せず、復帰後に①だけが最新条件で更新され、Jev要求を自動再送しないことを確認する。

Workerの版ずれfixtureは新入口の全5scopeで、Worker=A／ブラウザ=BとWorker=B／ブラウザ=Aを作る。取得先はBを返す状態にし、10分の通常キャッシュ期限前と、通常の裏更新が進行中の場合を分ける。一致へ更新できた場合は明示POSTが1回、Jevが最大1回であることを確認する。更新後も不一致・取得失敗・期限切れ・間隔制限中は`failed/index_updating`・`complete=false`・`cached=false`・空resultsとなり、IP／全体カウンターとJev呼出が0、古い判定結果キャッシュも採用されないことを確認する。検査済みsnapshotの有無によるsearchedのgeneration／nullとcandidates=judged=0を検証する。同時要求・偽generationの連打・ある要求の中断・遅い旧取得の完了でも更新Promiseを共有し、取得回数・間隔制限・snapshotの原子的な採用を守る。tools/gameは一覧と公開索引の更新が同じ処理に含まれることも確認する。ブラウザは`index_updating`のsearchedがnullでも復帰1回枠を使い、②や計測を自動再送しない。旧入口は新しいgeneration照合を必須化せず、Phase 3の回帰結果を維持する。

旧HTML互換fixtureには公開済み404・日刊ポータル・号ページと、それらが使う旧daily-ui.jsなどを保存する。旧版query付きURLへ新しいsite-search.jsを返し、search-ui.js／CSSは提供しない。旧rankの引数・返り値・メソッド・state/disabled・コールバックを固定し、成功・0件・失敗・停止・上限・入力変更・中止・言語／filters・①との重複除去と計測が旧契約で動くことを検証する。readResponseの旧応答fixtureも保持する。新UI側はcreateRankClient/readRankResponseを使い、旧描画を呼ばず、結果行・状態・イベント・計測が二重に発生しないことを確認する。

### 3.2 指標

- 必須例と公開対象・文字検索保持・版照合・操作・URL安全の契約ケースは100%通過。
- 一般語finalの読み検索recallは95%以上を目標とする。分母は事前に読みを付けた語で、辞書が読めなかった語を後から除かない。文字検索で救えた結果とは分けて集計する。
- 完全な語・適切なfiltersで正解が一意のケースは、正解を上位6件に含める。1文字の順位では利用者の意図を推測した正解を作らない。6件を超える場合は件数と全候補一覧への到達も評価する。
- 品詞・表記差による誤一致は語ごとに記録し、許容していない別語に広がる規則を増やさない。
- 読みの準備失敗で文字検索結果が変わるケース、同じ階層で4区画だけ強調されるケースは不合格。

### 3.3 新scopeのJev評価

新scopeごとに最低40問、tune/final各20問をAPIを見る前に固定する。各セットには正解あり10問以上、正解なし5問以上、filters／別scopeの境界5問以上を含める。題名の文字一致だけでなく目的の言い換え、逆機能、説明にない機能、複数の適切な候補を含める。公開済みのsite・日刊評価を新scopeの合格へ転用しない。

shortlistの候補到達率は一般の正解ありfinalで95%以上、必須のscope／filtersケースは100%を条件にする。Jev判定後は正解ありfinalの95%以上で適切な候補が上位5件に入り、正解なし・scope／filters外だけに正解があるfinalでは誤結果0件を条件にする。候補到達と判定を別集計し、finalを見て正解を書き換えない。未達ならtuneと実装を修正し、未見finalを新しく用意して再評価する。
