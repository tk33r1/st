# サイト内検索 Phase 3 PRD

草案（2026-10-09）。設計着手済み・未実装・未公開。

Phase 2 の [PRD](site-search.md) を引き継ぎ、日刊2誌・ツール一覧・ゲーム一覧への展開を具体化する。作り方は [設計書](site-search-phase3-design.md)、順番は [実装計画書](site-search-phase3-plan.md)、合否は [検証計画書](site-search-phase3-verification.md) に置く。Phase 3 の追加・変更案は本書を参照し、Phase 2 の公開済み仕様と混同しない。新しい案は本書の8章にまとめる。

## 1. 目的と対象

入力した語を含む検索に加え、目的を文で書く・言い換える・英語で探す場合も、対象の範囲でページや記事を見つけられるようにする。

| 画面 | scope | 探すもの | ①の正本 | ②・③の正本 |
| --- | --- | --- | --- | --- |
| `/tools/` | `tools` | ツール | `data/tools.json` | `data/site-search.json` の tool |
| `/game/` | `game` | ゲーム | `data/game.json` | 同索引の game |
| `/job/nitoridaily/` | `nitori` | 日刊ニトリの記事 | 同媒体の検索索引 | 同媒体の検索索引 |
| `/job/retailtechdaily/` | `retail` | リテールテック日刊の記事 | 同媒体の検索索引 | 同媒体の検索索引 |

日刊の号ページのヘッダー・タグはポータルへ引き継ぐ入口とし、号ページに②・③を新設しない。404 の `site`、MAGI チャット、トップページ・アプリのサイト案内、個別ツール・ゲームの処理内容は今回の新機能の対象外。ただし③の共通化に伴う404の回帰確認は行う。

手元の確認基点は `51401262` と未コミットの変更（2026-10-09）。観測した対象数はツール9件、ゲーム8件、日刊ニトリ169記事、リテールテック198記事。日刊は両誌とも `years: ["2026"]`。数は仕様の上限ではなく、この時点の観測値。複数年は模擬索引で確認する。

## 2. 利用者の操作

### 2.1 共通の3段階

1. ①キーワードの一致：既存のローカル検索。②・③を自動で送らない。
2. ②検索：Enter・検索ボタンを押したときだけ、Worker経由でJevによる判定を行う。①の上に別の結果欄を出す。
3. ③Shinya Takeda AIに聞く：利用者がボタンを押したときだけ、そのscopeと絞り込みの範囲で案内する。

②を送る前に①が0件なら検索ボタンを目立たせる。②の読み込み中は③を実行できない。②の完了・失敗後、または一度検索した条件を変えた後は③を選べる。空入力・IME変換中は送らない。

②が完全な結果を出したときは③を控えめに残す。一部の判定欠落・該当なし・失敗では③を目立たせる。正常な絞り込みで対象が0件と分かった場合は③を送らず、絞り込みの変更へ誘導する。

入力・対象の絞り込みが変わったら、②・③を中止し、古い結果を隠す。A→B→Aでも最初のAの応答を復活させない。並べ替えは①の表示順だけを変え、②・③を再送しない。

### 2.2 ツール・ゲーム

- 入力中の①は従来どおりカードを絞り込む。並べ替えと既存のカード操作を維持する。
- 検索ボタンを追加し、②をカード一覧の上に出す。②の結果順は①の並べ替えとは独立する。
- カテゴリ・ジャンルは①・②・③すべてに効かせる案とする。見えている絞り込みと送信する対象を一致させるため、Phase 2 の「filtersは日刊だけ」を拡張する（8章）。
- ②に出たページは①から一時的に除き、②を隠したら①へ戻す。①の件数・計測は除く前の件数を使う。
- ツールのサンプル表示、ゲーム一覧の取得失敗を「①の検索結果0件」として比較に使わない。②はWorkerの完全な索引が使えれば独立して実行できる。

### 2.3 日刊2誌

- 既存の横断検索フォームに②・③の結果欄を追加する。通常の送信は①と②を実行する。
- ヘッダー検索・タグ・`#q=` の受け取りでは①だけを実行する。②へ進むには検索ボタン・Enterを押す。
- カテゴリー・地域・月の変更では①を実行し、②・③は隠すだけ。再送しない。
- ①と②の重複判定には号のパスと記事アンカーを使う。同じ号の `#art-1` と `#art-2` は別記事。
- 検索対象はその媒体の全年度。①の日本語の空白処理を見直す場合は別の作業として扱い、②の精度改善と混ぜない。

## 3. 検索範囲と「見つからない」の意味

| 対象 | ②へ渡す候補 | ③のページ選びへ渡す候補 |
| --- | --- | --- |
| ツール・ゲーム | 絞り込み後の全件 | 全件を既存の件数・文字数上限内で渡す |
| 日刊 | 絞り込み後、文字の一致順と新しい記事で最大20件 | 同じ選び方で最大40件・16,000文字 |

値の正本は `personas.js`。上限・閾値はブラウザから指定できない。③に全件を渡せなかった場合は、ツール・ゲームでも探索範囲を限定した表現にする。

②の `complete` は「送った候補の判定が全部そろった」であり、全対象の探索完了を意味しない。画面は `searched.total`（絞り込み後の対象数N）、`candidates`（送った候補数M）、`judged`（有効な判定数J）を区別する。

- M=N、J=Mで該当なし：この絞り込みの対象では見つからなかったと表示できる。
- M<N、J=Mで該当なし：「対象N件のうち、文字の近い記事と新しい記事M件を調べましたが、意味の近い記事は見つかりませんでした」。全記事に無いとは書かない。
- J<M、結果あり：結果と判定の欠落を表示する。結果なし：失敗として扱う。
- 索引の欠落・取得失敗：対象0件に変換しない。①を残し、再試行を案内する。
- ③は検証済みの候補だけを根拠に答え、調べたN・Mを画面にも表示する。候補外の記事や機能を推測で「無い」と断定しない。

## 4. 送信とプライバシー

検索ボタンの近くに②の送信、③のボタンの近くに追加の送信を説明する。詳細はダイアログに置く。既存404の送り先・学習・保持期間の説明を出発点にし、公開直前に公式資料と照合する。新しい法的・料金の事実は、この草案では確定しない。

検索語をURL・参照元・サイトのDB・運用ログ・通知へ残さない。GA4に送る場合だけ、`assets/search-analytics.js` でメールアドレスと長い数字を伏せ、100コードポイントまでの `search_term` にする。計測停止時は検索イベントを送らない。伏せ字部品の取得失敗時も生の検索語を送らない。

ツール・ゲーム一覧の既存 `?q=` は、日刊と同じ受け渡し方式へ移行する。headで計測より先に消し、①だけに引き継ぐ。新しいリンクは `#q=` を使い、受け取ったら消す。受け付けない値もURLから消す。

`/tools/` の例外は一覧だけ。CSPの `connect-src` にWorkerのoriginを追加し、ブラウザから各AI会社のAPIへ直接送らない。個別ツールのCSP・処理・通信先を広げない。一覧の注記・FAQ・JSON-LDとAGENTS.mdを同じ公開単位で更新する。既存のClarity除外を解除しない。

ゲーム一覧もClarityの収集対象から外す。404・日刊の既存の了承をゲームへ広げない。入力欄に加え、検索語を表示する①②③の見出し・結果欄も対象とする。一覧での除外を実通信で確認できない場合は、その一覧のGTM読み込みを停止した状態で公開する。計測を止めた範囲は公開記録に残す。具体的な経路と検証は設計書7章・検証計画書5章による。

## 5. 費用・停止・障害

②の60回/IP/UTC日・全体3,000回/UTC日、③の10回/IP/UTC日・全体20回/UTC日を全scopeで共有する。scopeを変えて上限を回避できない。キャッシュ応答も②の回数に数える。費用の増加は候補数と実測usageから記録し、料金の単価をここに複製しない。

②の全体6秒・Jev2秒・画面8秒を維持する。③の期限も既存の値を引き継ぐ。通知は要求とは別の5秒。切断後に上流の呼び出しを続けず、確定した通知は独立して期限内に終える。

全体の停止とscope単位の停止を用意する。停止した②・③は①を維持する。部分的な日刊索引を利用可能に見せず、24時間以内の完全なスナップショットがある場合だけ代用する。

③は設定による停止と一時障害を区別する。停止だけで③を隠し、索引・上流などの一時障害では明示的な再試行を残す。停止後の再開はWorkerの設定を戻し、画面を再読み込みして確認する。自動の送信で再開を探らない。日刊索引の整合性は、取得した世代の全年度のdigestで確認する。新しい版が取得中に公開されても、整合した旧世代をその理由だけで拒否しない。世代が混在した取得のキャッシュを破棄し、次の明示検索で読み直せるようにする。

## 6. 受け入れ条件

| ID | 条件 |
| --- | --- |
| P3-R01 | 明示操作でだけ②・③を送り、初期表示・引き継ぎ・絞り込み・並べ替えでは送らない |
| P3-R02 | scopeと絞り込みが①・②・③で一致し、scope外のリンクを返さない |
| P3-R03 | 古い応答を捨て、IME・長押し・キャンセル・フォーカス維持をPhase 2と同等に満たす |
| P3-R04 | 全年度を完全に読み、年の混在・欠落を「対象0件」にしない |
| P3-R05 | 日刊の候補20件と③の拡大候補を区別し、未探索の対象について無いと断定しない |
| P3-R06 | 同じ号の別記事を保ち、①②の重複を正しい粒度で除く |
| P3-R07 | 生の検索語をURL・参照元・DB・運用ログ・通知・許可していない計測へ出さない |
| P3-R08 | ツール一覧だけに通信の例外を設け、個別ツールの約束を維持する |
| P3-R09 | ②③の上限・期限・停止が機能し、404・MAGI・アプリの既存通信と互換性がある |
| P3-R10 | scopeごとの精度・探索範囲・応答時間が検証計画書の基準を満たす |
| P3-R11 | 日英、明暗、320px、200%拡大、キーボード・読み上げで検索と状態を利用できる |
| P3-R12 | scopeごとに段階公開・停止でき、失敗したscopeが既存公開scopeへ影響しない |

## 7. 今回作らないもの

埋め込み検索・外部ニュース検索・記事本文の新しい収集・自動のAI送信・検索条件の共有URL・アプリの新しい検索画面は含めない。索引に検索用の言い換え語を追加する案は、日刊の候補選びが評価で基準を満たさないと分かった場合に別途設計する。
